0.

Introduction

This manual describes the command-line tools in ~/bin. The tools fall into two groups. Standalone tools have no external dependency. mrk tools are symlinks into the mrk repository, and mrk manages them.

Note
All the tools are bash scripts or Go binaries. Two shared libraries supply the common behavior. scripts/lib.sh serves the mrk install-phase scripts. bin/lib/common.sh serves the standalone tools. See Section 3.1.
Asking a Command What It Does
Every command in this manual answers -h and --help by printing a usage summary and exiting 0, and refuses any argument it does not recognise with exit 2. Both halves are deliberate. A script with no option parser does not ignore an unrecognised flag — it runs, with the flag discarded. Twelve commands here behaved that way until 2026-09-10, so mrk-uninstall --help unlinked ~/bin and mrk-post-install --help installed applications. This manual has 39 command entries, one for each executable mrk puts on the PATH — status and mrk-status are two names for the same binary, and bin/lib/ is a directory rather than a command. Thirty-eight of the 39 answer --help and refuse an unknown argument with exit 2. An option given without its value, or with a value it cannot use, is a wrong command line too and also exits 2 — pushall --projects with no directory, snapshot-keys -o "", prune-deployments --keep abc. Until 2026-09-10 five options exited 1 when their value was missing, four of them with bash's own message and no usage. decloud is the single exception and forwards every argument to git by design. The usage summary goes to stdout, so restore-repos --help | less shows it; five commands sent it to stderr until 2026-09-10, where a pipe saw nothing. mrk-picker keeps its help on stderr by design: its stdout is the selection it hands back to mrk-brew. Where a command takes no options of its own, the contract comes from mrk_help_guard in scripts/lib.sh; the two LaunchAgent scripts spell it out inline so that an unattended job depends on nothing but itself. Exit 2 always means the command line was wrong and nothing was attempted. A command that ran and then failed exits 1, so the two are worth telling apart: restore-keys nope.gpg exits 1 because the archive is missing, while restore-keys a.gpg b.gpg exits 2 because it never started.
Scope — This Documents One Machine
mrk is a personal system. It sets up my Mac, keeps it in that state, and moves it to the next machine. The tools below are general. Their data is not. The package list, the login items, the Dock, the preference domains and the private preferences repository are all personal choices. Read this manual for what each command does. Change those lists before you run any command on a different machine. Several commands delete files or change system settings.

Standalone Scripts

no external dependency
1.1

nuke-mrk standalone

Caution
nuke-mrk deletes data. It asks you to confirm first. It does not uninstall the Homebrew packages, and it does not roll back the macOS defaults.

nuke-mrk deletes all the mrk files, so that you can install mrk again. It moves ~/mrk and ~/.mrk to the Trash, and deletes the mrk symlinks in ~/bin, the dotfile symlinks in $HOME, and the ~/Projects/CLAUDE.md link.

nuke-mrk [--help | -h]
  • Before it deletes anything, nuke-mrk lists what exists only on this machine: any uncommitted change, commit on no remote, or stash in ~/mrk or ~/.mrk/preferences. It then stops, exit 1, "nothing has been deleted", unless you answer y. The fresh clone it tells you to make cannot contain any of it. Until 2026-09-11 it trashed all of that with "✔ Nuked." and no warning.
  • That included its own pre-nuke Brewfile sync: sync -c commits and does not push, so the commit went to the Trash with the repository and never reached the fresh clone. nuke-mrk now pushes that commit — only when it is the one commit waiting and touches only the Brewfile, so it never publishes other work of yours. snapshot-prefs already pushed its half.
  • The ~/Projects/CLAUDE.md link that mrk-post-install makes into assets/ is removed as well, and so are links left in ~/.local/bin by an old installation. Until 2026-09-11 the CLAUDE.md link survived the nuke, pointing at a repository in the Trash.
  • nuke-mrk leaves the login items alone, and that is deliberate. It does not uninstall Homebrew packages, so every application those items point at survives the run — the login item is a preference about an application that is staying, not an mrk artifact being cleaned up. Removing them was tried and reverted on 2026-09-10: the reinstall re-adds them, so the end state is identical, while add_login_item creates with hidden:false hardcoded and at end, which would silently reset any item you had set to launch hidden and rebuild the order as post-install's rather than yours.
  • On the reinstall, mrk-post-install therefore logs Login item exists for each one and skips it. To exercise the registration path instead, remove a single item by hand and re-run post-install.
  • nuke-mrk shows the reinstall instructions when it completes.
1.2

snapshot standalone

snapshot exports the current app preferences as plists into ~/mrk/assets/preferences/.

snapshot [--brewfile] [--help]
  • snapshot writes the plists and then stops. It does not commit or push them, and gitignore excludes them.
  • snapshot does not scan the exported plists for secrets, because it commits nothing. The commands that commit — snapshot-prefs, mrk-push and pushall — scan what they commit.
  • snapshot exports ~/Library/Preferences/ID.plist when that file exists, and the sandbox container's copy otherwise. Until 2026-09-11 it worked out that order and then exported by bundle id regardless, which reads the container's copy whenever there is one; none of its ten apps had a stale container, so no export was wrong.
  • --brewfile — also runs brew bundle dump. This command overwrites the comments in the Brewfile, so snapshot asks you to confirm first. When the dump holds no Mac App Store entries but the Brewfile it replaced did, snapshot puts them back from Brewfile.bak: brew bundle dump lists only the apps mas list reports, and with Spotlight indexing off that is none, so until 2026-09-10 a dump here silently dropped all 22.
  • Apps: AlDente, Amphetamine, BetterSnapTool, Descript, Fission, HandBrake, Helium, Ice, iTerm2, ScreenFlow
1.3

decloud standalone

decloud runs git against the private Cloud overlay for DoublEnder. The overlay files sit inside the public DoublEnder tree, and the public repository ignores them. A bare repository holds them, and it shares the same working tree. decloud passes every argument straight to git.

decloud <any git command>
  • decloud status — Show the state of the overlay files.
  • decloud commit -am "message" — Commit the overlay files.
  • decloud push — Push the overlay repository.
  • decloud reads the repository path from DECLOUD_GIT_DIR. The default is ~/DoublEnder-cloud.git.
  • decloud reads the working tree from DECLOUD_WORK_TREE. The default is ~/Projects/DoublEnder.
  • decloud sets core.hooksPath when the tracked pre-commit hook is present and the setting is absent. A fresh clone therefore gets the hook.
  • decloud exits with status 1 when the repository or the working tree is absent.
  • pushall does not push the overlay, but it reports the overlay's unpushed commits and its uncommitted changes. It finds the changes through the overlay's core.worktree setting, so keep that set.
  • Every decloud command prints warning: core.bare and core.worktree do not make sense, because the overlay's configuration sets both. The warning is harmless: decloud passes the working tree itself.
Caution
Stage the overlay files by name. decloud add . stages every untracked file in the shared working tree, which includes the files of the public repository.

2.1

check-updates mrk

check-updates checks whether the mrk repository has new commits. It runs at most once every 7 days. If your copy is behind, it asks you to update.

check-updates [--help | -h]
  • -h, --help — Show the usage summary and exit. Until 2026-09-10 check-updates had no option parsing, and the flag was discarded. That mattered more than it looks: before check-updates reaches its prompt it writes the rate-limit timestamp and disowns a background fetch, so check-updates --help consumed the week's check.
  • check-updates runs only in an interactive shell.
  • check-updates never waits for the network. It compares your copy against the last commit that git fetched, and it refreshes the remote in the background.
  • check-updates exits and shows nothing when your copy is current.
  • check-updates keeps the timestamp in ~/.cache/mrk/.
  • check-updates compares against the remote's default branch and falls back to main when the repository has no origin/HEAD. Until 2026-09-11 that fallback was unreachable: the lookup ran through a pipe under pipefail, so a missing origin/HEAD ended the script silently — every week, after it had written the timestamp and before any fetch that could restore the ref. A clone always has one, so this Mac was never affected.
2.2

doctor mrk

doctor checks that ~/bin is on the PATH. The --fix option adds a PATH line to ~/.zshrc.

doctor [check | --fix | fix] [--help | -h]
  • check (the default) — Shows the result and exits with status 0 or status 1.
  • -h, --help — Show the usage summary and exit.
  • --fix or fix — Adds the line to ~/.zshrc. doctor writes the line only when the line is absent, so you can run this command more than once. The line it adds first checks that ~/bin exists and that the PATH does not already contain it.
  • doctor reads only its first argument. Until 2026-09-10 a second one was discarded in silence, so doctor check --fix ran the check and dropped the --fix without saying so. It now exits 2 rather than ignoring the extra argument.
Note
To run the fix through Make, use make doctor ARGS=--fix. Make reads the bare form make doctor --fix as a Make option and fails.
2.3

fix-exec mrk

fix-exec sets the executable bit on the mrk scripts. It also sets the bit on the ~/bin symlinks that point into the repository. You can run fix-exec more than once.

fix-exec [--help | -h]
  • fix-exec removes a ~/bin symlink that points into the repository at a file that no longer exists — what a deleted or renamed script leaves behind. It touches no other link and no real file. Nothing else removes these: mrk-setup links only the scripts that exist. That is why it is the fix status offers for a broken tool link. Its help text said nothing about the removal until 2026-09-11.
2.4

harden mrk

Warning
harden changes system files, and it needs sudo. It writes the rollback script to ~/.mrk/hardening-rollback.sh before it changes anything. To undo the changes, run bash ~/.mrk/hardening-rollback.sh.

harden applies six optional macOS settings. It asks you to confirm each one. Five of them raise the security floor. One lowers it, and the list says which.

harden [--yes | -y] [--help | -h]
  • Touch ID for sudo — Adds pam_tid.so to /etc/pam.d/sudo.
  • Immediate password after sleep — Sets the screensaver password delay to 0.
  • Firewall and stealth mode — Turns on the macOS application firewall. harden checks the firewall state and the stealth mode state separately, so it can turn on stealth mode when the firewall is already on.
  • Mac Analytics — Stops the submission of usage and crash data to Apple. This needs sudo, because the key is in a system plist. It is the third telemetry channel; defaults.sh already turns off Siri data sharing and personalised advertising.
  • Handoff — Stops this Mac advertising its activity to nearby Apple devices, and stops it receiving theirs. The keys are ByHost, so harden writes them with defaults -currentHost.
  • Quarantine prompt — this step lowers the security floor. It sets LSQuarantine to false. macOS then does not show the "downloaded from the Internet" dialog on the first launch of an application. Gatekeeper still runs. The signature check and the notarization check are unchanged, and macOS still refuses an unsigned application. Only the extra confirmation goes away.

hide_tm.sh mrk

hide_tm.sh hides the Time Machine backup volumes from the Finder sidebar.

hide_tm.sh [volume_name] [--help | -h]
TM_VOLUMES="Vol1,Vol2" hide_tm.sh

snapshot-prefs mrk

Caution
snapshot-prefs scans every staged file for API keys and tokens before it commits. If the scan finds a match, snapshot-prefs stops and asks you to confirm. It does not ask when NONINTERACTIVE=1 is set or when there is no terminal — in those two cases it aborts. Read the reported lines before you answer.

snapshot-prefs exports the app preferences and pushes them to the private mrk-prefs repository. It exports plists for 18 named applications, and every io.github.sevmorris.* domain as a group. It also copies the Application Support files and the config directories.

The group export takes my own applications without naming them, because that list changes when I ship something new and a hand-written list would go out of date. Magic Backup Machine carried these preferences before 2026-09-02, inside an rsync mirror that keeps the current state and no history.

snapshot-prefs [--help | -h]
  • Apps: BetterSnapTool, Ice, iTerm2, Raycast, Stats, Loopback, SoundSource, Audio Hijack, Farrago, Piezo, Typora, Keka, TimeMachineEditor, MacWhisper, Helium, Descript, Waves Central, MusicBrainz Picard
  • Application Support: Loopback (devices and routing), SoundSource (presets and sources)
  • Config directories: Calibre (~/Library/Preferences/calibre/). Calibre keeps a tree of files, not a defaults domain, so snapshot-prefs copies the files. ~/.config/MusicBrainz is deliberately not copied: Picard writes its OAuth tokens into the same INI as its settings.
  • snapshot-prefs converts each binary plist to xml1 before it scans the file, because the scan cannot read a binary plist.
  • The scan before the commit covers every staged file that carries content, fonts excepted. Until 2026-09-10 it skipped a renamed file: git add -A stages a plist whose name changed as a rename, and the list the scan read held only added and modified files, so a secret in it went unread.
  • snapshot-prefs records every git repository in ~/Projects that has an origin remote in repos.tsv, the manifest restore-repos clones from — including one kept a folder down, such as JustIn/JustIn, which it names by that path. The list is the one pushall sweeps. It warns about a repository with no origin, and it names the folders it cannot record because they are not repositories; until 2026-09-10 those were left out without a word.
  • snapshot-prefs refuses to start while a merge, rebase or cherry-pick in ~/.mrk/preferences is unfinished, or while a file there has unresolved conflicts, and exits 1. It checks before it exports anything. pull-prefs pulls with --ff-only, so only a git command run by hand leaves the repository in that state.
  • snapshot-prefs skips an app that is not installed, and it reports the skipped apps when it exits.
  • snapshot-prefs does not quit any app. defaults export asks the preferences system, which has an open app's changes as soon as it makes them — measured with a running test app whose change was visible to defaults export before the app had quit or synchronised. Until 2026-09-11 its help text, this page, the manual and SMAC-1 all said it quit each app first; it never had.
  • It reads each app's preferences where the app keeps them: ~/Library/Preferences/ID.plist when that file exists, and the app's sandbox container otherwise (prefs_source in scripts/lib.sh). Asked by bundle id alone, defaults prefers the container's copy whenever there is one, and a container outlives the sandboxed build that wrote it. Five of my own apps have one, and until 2026-09-11 snapshot-prefs saved those abandoned copies instead of the live settings — months out of date, and for JustIn and WaxOn missing their settings entirely.
  • An app with no preferences here yet is skipped, and the copy saved from before is kept. defaults export does not fail on an absent domain: it writes an empty dict, which replaced the saved copy and was pushed. BetterSnapTool reaches that state on a new Mac, because it comes from the App Store and is installed after mrk-post-install has run.
  • The group of my own apps is listed by defaults domains, so a sandboxed app's domain, which exists only in its container, is included — FL2601's is one. Empty domains are left out: ClipHack's tests leave one behind for each test process, and ten of them had been saved.

status mrk

status is a two-pane TUI dashboard. It shows the health of the mrk installation. The same binary also runs as mrk-status.

status
mrk-status [--help | -h]
  • Left pane — eight checks, each with a ✓, ⚠ or ✗ mark: dotfiles, tool symlinks, macOS defaults, security hardening, shell, PATH, Homebrew, and Brewfile packages. A ninth, Backups, appears only when ~/.mrk/backups holds at least one directory, and it appears fifth, between security hardening and shell — not appended at the end.
  • Right pane — the detail lines for the selected check. The pane also shows the suggested fix command.
  • f — Run the fix command for the selected check.
  • r — Run all the checks again.
  • tab / ←→ — Move to the other pane.
  • Until 2026-09-10 mrk-status compared only its first argument against --help and -h and opened the dashboard on anything else, so an unrecognised flag was discarded. The same was true of mrk-menu. Both now exit 2.
  • make status is a different program: scripts/status, which prints the same checks as plain text and is linked nowhere in ~/bin. On a healthy machine the two agree on every check. Until 2026-09-11 they parted in the failure branches, each having had a fix the other lacked. When brew list failed, make status listed all 128 Brewfile packages as not installed — the P-4 defect fixed here on 2026-09-09. And this dashboard offered the bare chsh that make status had stopped offering on 2026-09-10, for the reason in the next item.
  • The Shell fix is chsh -s <zsh> only when that zsh is listed in /etc/shells. chsh refuses a shell that is not, and on a new Mac Homebrew's zsh is not: make all runs Phase 1 before Phase 2 installs it. Then the fix is make setup ARGS="--only shell", which registers the shell and sets it.
  • The Tools fix for a broken link is make fix-exec, which removes a link whose script is gone. Until 2026-09-11 it was make setup, which links only scripts that exist: pressing f re-ran all of Phase 1, left the link broken, and offered the same fix again. A test now runs the fix and requires the check to pass afterwards, because a fix command that merely exists passed the earlier gate.
2.9

sync mrk

sync compares the installed Homebrew packages against the Brewfile. It shows a picker for the new packages. It then adds the packages you select to the correct section, in alphabetical order.

sync [--dry-run | -n] [--commit | -c] [--prune | -p]
  • --dry-run — Shows the additions and the deletions. sync does not change the Brewfile.
  • --commit — Commits the Brewfile after sync updates it.
  • --prune — Deletes the Brewfile entries for the packages that you uninstalled. You select which entries to delete.
  • sync uses mrk-picker for the selection. If mrk-picker is absent, sync uses gum.
  • sync drops the names that ~/.mrk/sync-ignore lists. The file holds one formula name or cask name per line, and a # character starts a comment.
  • After you select the new packages in the picker, sync offers the packages you declined, so you can add them to the ignore list. It creates ~/.mrk/sync-ignore when you accept, and you can also write the file yourself. The offer changes only the ignore list, never the Brewfile. If you decline it, sync writes nothing and offers the same packages again on the next run. With --dry-run it shows the names but writes no file.
  • sync only adds to the ignore list. It keeps your comments, your blank lines and your order, and it adds each new name at the end.
  • If brew list fails, sync stops. As of 2026-09-10 sync also stops when brew list succeeds and reports nothing installed, which brew does on a machine where Homebrew has nothing installed yet. Staleness is "in the Brewfile, absent from the installed set", so an empty set would make --prune mark every entry for deletion. The check needs both the formula and the cask list to be empty — a machine with casks and no formulae is unremarkable — and applies only to --prune.
  • sync writes a new cask entry as cask "name", greedy: true, matching every other cask in the Brewfile. Without the modifier brew bundle skips a cask when upgrading anything that sets auto_updates or version :latest, so it would quietly stop being upgraded by make update.
  • sync writes the Brewfile to a temporary file first, and then moves it into place.
2.10

sync-login-items mrk

sync-login-items compares the system login items against the items that scripts/post-install tracks. It shows a picker, so you can add the new items or delete the old ones. It then updates scripts/post-install and docs/manual.md together.

sync-login-items [--dry-run | -n] [--commit | -c]
  • --dry-run — Shows the differences and your selections. sync-login-items writes no files.
  • --commit — Commits the changed files. The commit message has the form login-items: add X; remove Y.
  • sync-login-items uses gum for the multiple-selection list. If gum is absent, it asks a y/N question for each group.
  • sync-login-items reads the login items from System Events with AppleScript.
  • sync-login-items drops the names that ~/.mrk/login-items-ignore lists. The file holds one login-item name per line, without the .app suffix, and a # character starts a comment. Some apps add themselves back to the login items after an update, and the ignore list stops sync-login-items from offering them again.
  • After you select the new items to add, sync-login-items offers the items you declined, so you can add them to the ignore list. It creates ~/.mrk/login-items-ignore when you accept, and you can also write the file yourself. The offer changes only the ignore list. If you decline it, sync-login-items writes nothing and offers the same items again on the next run. With --dry-run it shows the names but writes no file.
  • sync-login-items only adds to the ignore list. It keeps your comments, your blank lines and your order, and it adds each new name at the end.
  • sync-login-items drops the ignored names from the new items only. A name in the ignore list does not delete an item that post-install already tracks. sync-login-items shows an app that is both tracked and ignored under "Ignored, but still tracked", and it offers to delete the app from scripts/post-install.
Caution
If System Events returns no login items, or if the AppleScript fails, sync-login-items stops and shows an error. It does not continue, because an empty list looks the same as a complete list of deletions, and sync-login-items would then offer to delete every tracked item. Give Automation access in System Settings → Privacy & Security → Automation, and then run the command again. If you really have no login items, edit the add_login_item block in scripts/post-install by hand.
2.11

mrk-install mrk

mrk-install is the mrk installer. It runs the setup phase, the brew phase and the post-install phase. Use it for a full bootstrap, or to run one phase again.

mrk-install [--brew | --post | --all] [options]
  • --brew — Run the brew phase.
  • --post — Run the post-install phase.
  • --all — Run all the phases, one after the other.
  • -h, --help — Show the usage summary and exit.
  • No flag — Run the setup phase only.
  • mrk-install passes the other options to the phase that you select.
2.12

mrk-setup mrk

mrk-setup is phase 1. It symlinks the dotfiles, symlinks the tools into ~/bin, sets the shell, installs oh-my-zsh and its plugins, and backs up the files that it replaces. You can run mrk-setup more than once.

mrk-setup [--only PHASE] [--dry-run] [--yes] [options]
  • --only PHASE — Run a single phase. One of xcode, dotfiles, tools, defaults, shell.
  • --no-dotfiles — Skip linking the dotfiles.
  • --no-defaults — Skip the macOS defaults.
  • --no-link-tools — Skip linking scripts/ and bin/ into ~/bin.
  • --dry-run — Preview the changes and apply none of them.
  • --validate — Validate the configuration before installing.
  • --continue-on-error — Carry on with the remaining phases when one fails.
  • --debug — Trace execution with set -x.
  • -y, --yes — Answer every prompt yes. Use for unattended runs.
  • -h, --help — Show the usage summary and exit.
  • MRK_LOGIN_MSG — When set, mrk-setup writes that text to the login window. This needs sudo, and the undo line is appended to ~/.mrk/defaults-rollback.sh.
  • mrk-setup sets the login shell, registering it in /etc/shells first — chsh refuses a shell that is not listed there, and Homebrew does not register its own zsh.
2.13

mrk-brew mrk

mrk-brew is phase 2. It installs the Homebrew formulae and casks that the Brewfile lists. The Mac App Store applications the Brewfile lists as mas entries it does not install: it ends every run with the one command that does.

mrk-brew [options]
  • -n, --dry-run — Report what would be installed and change nothing.
  • -y, --yes — Answer every prompt yes. Use for unattended runs.
  • --no-casks — Install the formulae only, skipping the GUI applications.
  • --no-formulae — Install the casks only.
  • --only-formulae — Install the formulae only.
  • --skip-brew-install — Assume Homebrew is present and do not install it.
  • --debug — Verbose output.
  • -h, --help — Show this help.
  • The short -n was added 2026-09-10. Before that mrk-brew took --dry-run only, so make brew ARGS=-n failed with "Unknown option" although the Makefile advertises ARGS=-n for sync.
Caution — the App Store Apps Are Listed, Not Installed
mrk-brew leaves the Brewfile's mas entries out of every brew bundle run and ends with this command, to run by hand once App Store.app is signed in: grep '^mas ' ~/mrk/Brewfile | sed 's/.*id: //' | xargs sudo mas install. It cannot do this itself. brew bundle installs a mas entry with mas install, which mas 7 documents as requiring root, and brew never runs anything as root. The mas entries were added on 2026-09-10 with the claim that make brew would reinstall them; it never did. Its interactive path had skipped every mas line since the first commit, and its --yes path handed them to brew bundle, where each became a mas install without root.
  • Sign in to App Store.app by hand before that command: mas has had no signin command since macOS 12.
  • Run make post-install after that command, again if make all already ran it: it restores an app's preferences and login item only if the app is installed, and BetterSnapTool and Chrono Plus come from the App Store. mrk-brew's closing hint and make all's summary both say so.
  • brew bundle decides whether an App Store app is installed from mas list, and mas list reads the App Store id from Spotlight. With indexing off, which is how this machine is set up, it reports none: brew bundle check called all 22 installed apps missing, and brew bundle dump writes no mas lines. mas itself cannot see them either, so the command above may download every one again on such a Mac. Keep it for a new machine.
  • Add a new entry with mas search <name>, and confirm the id with mas info <id> before trusting it: App Store display names carry marketing suffixes the bundle names do not, and matching on name alone picked the wrong application for one of the 22.
2.14

mrk-post-install mrk

mrk-post-install is phase 3. It configures the apps that Homebrew installed. It imports the app plists, restores the Application Support files and the config directories, and registers the login items.

mrk-post-install [--yes | -y] [--help | -h]
  • -y, --yes — Answer every prompt yes. Use for unattended runs.
  • -h, --help — Show the usage summary and exit.

Caution
mrk-push scans every file the commit carries for API keys and tokens before it commits. If the scan finds a match, mrk-push stops and asks you to confirm. It does not ask when NONINTERACTIVE=1 is set or when there is no terminal — in those two cases it aborts. Read the reported lines before you answer. A file the scan cannot read counts as a match, not as clean.

mrk-push commits the mrk repository and pushes it. It then deletes the old GitHub Pages deployments with the GitHub CLI. If you give no commit message, mrk-push asks you for one.

mrk-push "commit message"
mrk-push                # mrk-push asks for the message
mrk-push --dry-run      # change nothing
mrk-push -- "-starts with a dash"
  • -n, --dry-run — Report what would be staged, committed, pushed and pruned, and change nothing. The secret scan still runs, so this doubles as an audit of what a push would expose. No commit message is needed.
  • -h, --help — Show the usage summary and exit.
  • -- — End option parsing, so a commit message can begin with a dash.
  • mrk-push takes one argument for the message, so quote it. Until 2026-09-10 it read only the first word and discarded the rest, so mrk-push fix the login bug committed fix without saying so. It now refuses and prints the quoted form you meant.
  • mrk-push refuses any other argument that begins with a dash. Before 2026-09-09 it had no option parsing at all and took every argument as the commit message, so mrk-push --help committed and pushed with --help as the subject.
  • mrk-push refuses to stage anything while a merge, rebase, cherry-pick or revert is unfinished, or while a file still has unresolved conflicts, and exits 1. git add -u would otherwise mark the conflicted files resolved with their conflict markers in, and the commit would conclude the merge.
  • Until 2026-09-10 the secret scan had three holes, each of which let a planted secret through in a sandbox. Run from a subdirectory such as docs/, mrk-push handed the scanner paths relative to the top of the repository, the scanner found none of them from where it stood, and it reported clean having read nothing. A renamed file and a symlink replaced by a file were left off the list entirely. A file with a non-ASCII name was listed in git's quoted form, which names no file. The list now comes from commit_paths in scripts/lib.sh, and check-commit-gates plants each case in a throwaway repository on every make check.
  • A commit that only deletes or renames files is committed. Until 2026-09-10 mrk-push decided whether there was anything to commit from the list of files it scans, which holds no deleted file, so it answered "Nothing to commit.", pushed without the change, left it staged and discarded the message.
  • mrk-push needs the gh CLI on the PATH.
  • Run mrk-push inside a git working tree.
  • mrk-push keeps the most recent GitHub Pages deployment and deletes the older ones.

check-commit-gates mrk

check-commit-gates proves that the commands which commit and push keep secrets and conflict markers off a remote. It builds throwaway repositories, each with a local bare remote, in a temporary directory, plants a case in each, and runs pushall and mrk-push against them.

check-commit-gates [--help | -h]
  • The cases are a secret in an ordinary file, in a file with a non-ASCII name, in a renamed file, in a symlink replaced by a file and in a file added by hand; a repository stopped mid-merge, mid-cherry-pick and with a conflicted git stash pop; mrk-push run from a subdirectory; and a commit that only deletes. Every one of them reached a remote, or lost a commit, in a sandbox before 2026-09-10.
  • Each refusal is checked against a control that must succeed — an ordinary change must be pushed — because a harness in which nothing is ever pushed would pass every "was refused" test.
  • It fails if the dry run of pushall and the real run disagree about which repositories they refuse. On 2026-09-10 the dry run caught a secret in a renamed file that the real run then pushed.
  • It checks that pushall names the work it does not push — a commit on another branch, a stash, a folder that is not a repository — in both modes, and that it does not mistake the current branch's own unpushed commit, which it is about to push, for work left behind.
  • It checks what counts as a project: a repository one level down in a folder that is not one is swept and pushed; a repository inside a repository, one two levels down, and a linked worktree are not.
  • It checks that pushall names the work in a repository named *.git directly in the home folder — DoublEnder's Cloud overlay is one — without committing or pushing it: an unpushed commit and an uncommitted change in an overlay shaped like the real one, and a bare repository with no working tree and no remote, which ended pushall with status 128 in the first version of that report.
  • pushall is run with --projects and --no-mrk, and HOME points into the temporary directory, so a regression in either flag still cannot reach ~/Projects or the mrk repository. The bare-repository cases are the exception, because --projects switches that report off: their one real run goes ahead only after the dry run has shown that the sandbox's own repository is all pushall swept, so a pushall that stopped honouring HOME would stop there.
  • check-commit-gates exits with status 1 when any case fails, and names it. ci-check runs it after the tracked-file secret scan, so make check covers it.

snapshot-keys puts ~/.ssh, ~/.gnupg and the code-signing identities into one archive. The archive is a symmetric OpenPGP message with AES-256 and ASCII armor. It asks for a passphrase.

snapshot-keys [-o PATH] [-n] [-f] [--no-signing] [--help | -h]
  • -o or --output PATH — Write the archive to PATH. The default is ~/Desktop/mrk-keys-<timestamp>.asc. A missing or empty PATH exits 2. Until 2026-09-10 a missing one exited 1, and -o "" quietly used the default.
  • -n or --dry-run — List the contents. snapshot-keys writes no file.
  • -f or --force — Overwrite the output file when it exists.

Seven of its eight Helium paths named folders Helium does not create; only its ~/Library/Caches line had ever removed anything.
  • It leaves Spotify's PersistentCache alone. That is Spotify's default offline-storage location, so the line that used to delete it would have removed every downloaded playlist once a day. Only ~/Library/Caches/com.spotify.client goes.
  • It does not wait for an application to quit. A calendar LaunchAgent that misses 03:00 while the Mac sleeps runs at the next wake, when the browsers are usually open. Chromium tolerates this: after the run at 18:37 on 2026-09-10, Helium, running throughout, rebuilt its 464 MB cache.
  • nuke-mrk and make uninstall unload the agent and delete it.
2.33

clear-derived-data mrk

clear-derived-data deletes the contents of the Xcode DerivedData directory. It keeps the directory itself.

clear-derived-data [--help | -h]
  • A LaunchAgent runs clear-derived-data every Sunday at 03:00. post-install installs the agent as com.user.clear_derived_data.
  • clear-derived-data exits with status 1 when HOME is unset or is not a directory.
  • nuke-mrk and make uninstall unload the agent and delete it.
2.34

trim-services mrk

trim-services turns off background launchd agents that this Mac does not need. These are jobs, not preference keys, so they are not in defaults.sh.

trim-services [-n | --dry-run] [--help | -h]
  • -n or --dry-run — List each agent and the cost of turning it off. trim-services changes nothing.
  • trim-services uses launchctl disable, which writes to the launchd override database. The plists of the Apple agents are under /System/Library/LaunchAgents, and SIP does not allow a change to those. The override database is writable, and a disabled job stays disabled after a restart.
  • SIP also refuses launchctl bootout on an Apple agent that runs already. trim-services reports that case as "takes effect at next login" rather than as stopped.
  • trim-services writes ~/.mrk/services-rollback.sh. Run bash ~/.mrk/services-rollback.sh to turn every agent back on.
  • Chrome installs its updater again when it next starts. Run trim-services again after a Chrome update.
  • trim-services is not part of make all. Run it through Make with make trim-services, or preview it with make trim-services ARGS=-n.
Caution
The Photos agents are the item with a real cost. Without photoanalysisd and mediaanalysisd, Photos does not build People albums or Memories, and Visual Look Up does not work.
2.35

build-tools mrk

build-tools rebuilds the three Go binaries — mrk-picker, mrk-status and mrk-menu — and relinks them into ~/bin. It wraps make -C ~/mrk build-tools rather than repeating the build, so there is only one build path to drift.

build-tools
  • -h, --help — Show the usage summary and exit.
  • build-tools needs Go on the PATH.
  • The binaries are gitignored build artifacts, and nothing warns you on its own that one is older than its source: make maintain reports it, but only when you run it. Run build-tools after changing anything under tools/, or you keep using the previous binary.
  • The Makefile stamps each binary with the version and commit from git describe --tags. That is why the v1.0.0 tag is kept even though its GitHub release was deleted — without a tag the binaries report a bare commit SHA.
2.36

check-defaults-desc mrk

check-defaults-desc verifies that the defaults reference documents every key scripts/defaults.sh writes. It compares the write_default calls against the DEFAULT_DESCRIPTIONS map in docs/defaults/script.js, in both directions.

check-defaults-desc [--help | -h]
  • check-defaults-desc exits with status 1 when a key has no description, and also when a description has no key — a stale entry is reported as well as a missing one.
  • ci-check runs it after check-picker-desc, so make check covers it.
  • It resolves the $domain loop variable in defaults.sh to that loop's first domain, so the trackpad keys are counted once rather than once per mirror domain.
