Introduction

This manual describes the command-line tools in ~/bin. The tools fall into two groups. Standalone tools have no external dependency. mrk tools are symlinks into the mrk repository, and mrk manages them.

Note
All the tools are bash scripts or Go binaries. Two shared libraries supply the common behavior. scripts/lib.sh serves the mrk install-phase scripts. bin/lib/common.sh serves the standalone tools. See Section 3.1.
Asking a Command What It Does
Every command in this manual answers -h and --help by printing a usage summary and exiting 0, and refuses any argument it does not recognise with exit 2. Both halves are deliberate. A script with no option parser does not ignore an unrecognised flag — it runs, with the flag discarded. Twelve commands here behaved that way until 2026-09-10, so mrk-uninstall --help unlinked ~/bin and mrk-post-install --help installed applications. This manual has 40 command entries, one for each executable mrk puts on the PATH — status and mrk-status are two names for the same binary, and bin/lib/ is a directory rather than a command. Thirty-nine of the 40 answer --help and refuse an unknown argument with exit 2; mrk-install does so by handing an argument it does not know to the phase script, which refuses it. An option given without its value, or with a value it cannot use, is a wrong command line too and also exits 2 — pushall --projects with no directory, snapshot-keys -o "", prune-deployments --keep abc. Until 2026-09-10 five options exited 1 when their value was missing, four of them with bash's own message and no usage. decloud is the single exception and forwards every argument to git by design. The usage summary goes to stdout, so restore-repos --help | less shows it; five commands sent it to stderr until 2026-09-10, where a pipe saw nothing. mrk-picker keeps its help on stderr by design: its stdout is the selection it hands back to mrk-brew. Where a command takes no options of its own, the contract comes from mrk_help_guard in scripts/lib.sh; the two LaunchAgent scripts spell it out inline so that an unattended job depends on nothing but itself. Exit 2 always means the command line was wrong and nothing was attempted. A command that ran and then failed exits 1, so the two are worth telling apart: restore-keys nope.gpg exits 1 because the archive is missing, while restore-keys a.gpg b.gpg exits 2 because it never started.
Scope — This Documents One Machine
mrk is a personal system. It sets up my Mac, keeps it in that state, and moves it to the next machine. The tools below are general. Their data is not. The package list, the login items, the Dock, the preference domains and the private preferences repository are all personal choices. Read this manual for what each command does. Change those lists before you run any command on a different machine. Several commands delete files or change system settings.

nuke-mrk standalone

Caution
nuke-mrk deletes data. It asks you to confirm first. It does not uninstall the Homebrew packages, and it does not roll back the macOS defaults.

nuke-mrk deletes all the mrk files, so that you can install mrk again. It moves ~/mrk and ~/.mrk to the Trash, and deletes the mrk symlinks in ~/bin, the dotfile symlinks in $HOME, and the ~/Projects/CLAUDE.md link.

nuke-mrk [--help | -h]
  • Before it deletes anything, nuke-mrk lists what exists only on this machine: any uncommitted change, commit on no remote, or stash in ~/mrk or ~/.mrk/preferences. It then stops, exit 1, "nothing has been deleted", unless you answer y. The fresh clone it tells you to make cannot contain any of it. Until 2026-09-11 it trashed all of that with "✔ Nuked." and no warning.
  • That included its own pre-nuke Brewfile sync: sync -c commits and does not push, so the commit went to the Trash with the repository and never reached the fresh clone. nuke-mrk now pushes that commit — only when it is the one commit waiting and touches only the Brewfile, so it never publishes other work of yours. snapshot-prefs already pushed its half.
  • nuke-mrk offers three rollback scripts: the defaults, the hardening and the services one, which trim-services writes. When you accept, it names the apps whose whole preferences the defaults rollback would delete, and asks about those separately, as mrk-uninstall does. Until 2026-09-27 the services one was neither offered nor kept, and one yes deleted every imported app's preferences.
  • If you decline to run the rollback scripts, nuke-mrk keeps all three — with ~/.mrk/plist-backups/, which the defaults one imports from — in ~/.mrk, and trashes the rest. The settings they undo are still in force, and a reinstall adds to the kept files rather than starting new ones that record mrk's own values as the originals. Until 2026-09-11 they went to the Trash with the rest: that is how this Mac lost its hardening undo script, and every original in its defaults one, at the reinstall of 2026-09-10.
  • The ~/Projects/CLAUDE.md link that mrk-post-install makes into assets/ is removed as well, and so are links left in ~/.local/bin by an old installation. Until 2026-09-11 the CLAUDE.md link survived the nuke, pointing at a repository in the Trash. So are the two Claude Code skill links it makes, ~/Projects/.claude/skills and ~/.claude/skills/dependency-updates, and the SessionStart hook it adds to ~/.claude/settings.json. Only that one entry goes, matched on its exact command with jq, and the rest of the file is left as it was. Until 2026-09-28 all three survived, and the hook ran a script that no longer existed at the start of every Claude Code session.
  • nuke-mrk leaves the login items alone, and that is deliberate. It does not uninstall Homebrew packages, so every application those items point at survives the run — the login item is a preference about an application that is staying, not an mrk artifact being cleaned up. Removing them was tried and reverted on 2026-09-10: the reinstall re-adds them, so the end state is identical, while add_login_item creates with hidden:false hardcoded and at end, which would silently reset any item you had set to launch hidden and rebuild the order as post-install's rather than yours.
  • On the reinstall, mrk-post-install therefore logs Login item exists for each one and skips it. To exercise the registration path instead, remove a single item by hand and re-run post-install.
  • nuke-mrk shows the reinstall instructions when it completes.

decloud standalone

decloud runs git against the private Cloud overlay for DoublEnder. The overlay files sit inside the public DoublEnder tree, and the public repository ignores them. A bare repository holds them, and it shares the same working tree. decloud passes every argument straight to git.

decloud <any git command>
  • decloud status — Show the state of the overlay files.
  • decloud commit -am "message" — Commit the overlay files.
  • decloud push — Push the overlay repository.
  • decloud reads the repository path from DECLOUD_GIT_DIR. The default is ~/Projects/DoublEnder-cloud.git.
  • decloud reads the working tree from DECLOUD_WORK_TREE. The default is ~/Projects/DoublEnder.
  • decloud sets core.hooksPath when the tracked pre-commit hook is present and the setting is absent. A fresh clone therefore gets the hook.
  • decloud exits with status 1 when the repository or the working tree is absent.
  • pushall does not push the overlay, but it reports the overlay's unpushed commits and its uncommitted changes. It finds the changes through the overlay's core.worktree setting, so keep that set.
  • Every decloud command prints warning: core.bare and core.worktree do not make sense, because the overlay's configuration sets both. The warning is harmless: decloud passes the working tree itself.
Caution
Stage the overlay files by name. decloud add . stages every untracked file in the shared working tree, which includes the files of the public repository.

check-updates mrk

check-updates checks whether the mrk repository has new commits. It runs at every shell start and fetches at most once a day. If your copy is behind, it asks you to update, once for each new remote head.

check-updates [--help | -h]
  • -h, --help — Show the usage summary and exit. Until 2026-09-10 check-updates had no option parsing, and the flag was discarded. That mattered more than it looks: before check-updates reaches its prompt it writes the rate-limit timestamp and disowns a background fetch, so check-updates --help consumed the week's check.
  • check-updates runs only in an interactive shell.
  • check-updates never waits for the network. At every shell start it compares your copy against the last commit that git fetched. It refreshes the remote in the background, at most once a day. Until 2026-09-30 the whole check ran at most once every 7 days, so a commit pushed the day after a check waited up to a week to be offered.
  • check-updates asks once for each new remote head. Answer no, or press Ctrl-D, and it stays quiet until the remote moves again; it prints the make pull command to run in the meantime. Shells that start together, as a restored terminal session starts them, ask once between them.
  • check-updates asks only when the default branch is checked out. make pull fast-forwards the checked-out branch, so on any other branch a yes would not pull the commits the prompt described.
  • check-updates exits and shows nothing when your copy is current, or has commits the remote lacks.
  • check-updates keeps its state in ~/.cache/mrk/: last-update-check, when the last fetch started, and asked-<commit>, the remote head it last asked about.
  • Answering yes runs make pull, which also rebuilds and relinks what the pulled commits changed. If the pull fails, check-updates says so, deletes its asked- record and exits with make's status, and the next shell asks again. Until 2026-10-01 the record stayed. Your copy was still behind, and nothing asked again until the remote moved.
  • check-updates compares against the remote's default branch and falls back to main when the repository has no origin/HEAD. Until 2026-09-11 that fallback was unreachable: the lookup ran through a pipe under pipefail, so a missing origin/HEAD ended the script silently — every week, after it had written the timestamp and before any fetch that could restore the ref. A clone always has one, so this Mac was never affected.
  • tests/check-updates.sh covers it; see ci-check.

doctor mrk

doctor checks that ~/bin is on the PATH. The --fix option adds a PATH line to ~/.zshrc.

doctor [check | --fix | fix] [--help | -h]
  • check (the default) — Shows the result and exits with status 0 or status 1.
  • -h, --help — Show the usage summary and exit.
  • --fix or fix — Adds the line to ~/.zshrc. doctor writes the line only when the line is absent, so you can run this command more than once. The line it adds first checks that ~/bin exists and that the PATH does not already contain it.
  • doctor reads only its first argument. Until 2026-09-10 a second one was discarded in silence, so doctor check --fix ran the check and dropped the --fix without saying so. It now exits 2 rather than ignoring the extra argument.
Note
To run the fix through Make, use make doctor ARGS=--fix. Make reads the bare form make doctor --fix as a Make option and fails.

fix-exec mrk

fix-exec sets the executable bit on the mrk scripts. It also sets the bit on the ~/bin symlinks that point into the repository. You can run fix-exec more than once.

fix-exec [--help | -h]
  • fix-exec removes a ~/bin symlink that points into the repository at a file that no longer exists — what a deleted or renamed script leaves behind. It touches no other link and no real file. Nothing else removes these: mrk-setup links only the scripts that exist. That is why it is the fix status offers for a broken tool link. Its help text said nothing about the removal until 2026-09-11.

harden mrk

Warning
harden changes system files, and it needs sudo. It writes the rollback script to ~/.mrk/hardening-rollback.sh before it changes anything. To undo the changes, run bash ~/.mrk/hardening-rollback.sh.

harden applies six optional macOS settings. It asks you to confirm each one. Five of them raise the security floor. One lowers it, and the list says which.

harden [--yes | -y] [--help | -h]
  • Touch ID for sudo — Adds pam_tid.so to /etc/pam.d/sudo_local, which /etc/pam.d/sudo includes on macOS 14 and later and which, in Apple's words in sudo_local.template, "survives system update". An existing sudo_local keeps its lines. /etc/pam.d/sudo itself is edited only on a macOS with no sudo_local. Every PAM file is written beside its target and renamed over it. Until 2026-09-11 harden overwrote /etc/pam.d/sudo in place, so a write that failed part-way left sudo's own PAM file truncated.
  • Immediate password after sleep — Sets the screen-lock delay to immediate with sysadminctl -screenLock immediate -password -, which asks for your login password, so this step runs only at a terminal; without one, harden reports the current delay and prints that command. Until 2026-09-11 it wrote the com.apple.screensaver keys askForPassword and askForPasswordDelay, which current macOS ignores: on this Mac they read "immediately" while sysadminctl -screenLock status reported the delay macOS enforced — 3600 seconds.
  • Firewall and stealth mode — Turns on the macOS application firewall. harden checks the firewall state and the stealth mode state separately, so it can turn on stealth mode when the firewall is already on.
  • Mac Analytics — Stops the submission of usage and crash data to Apple. This needs sudo, because the key is in a system plist. It is the third telemetry channel; defaults.sh already turns off Siri data sharing and personalised advertising.
  • Each setting's undo line is recorded once, on the first run, and a later run leaves it alone. Until 2026-09-11 that held only for a key present on the first run: for Mac Analytics and Handoff, a key that was absent got a delete line, and a second run then added a line recording mrk's own value, so the undo ended on mrk's value. ThirdPartyDataSubmit, turned off with Mac Analytics, had no undo line at all.
  • An undo file already there keeps its lines whatever its first line says. harden sets it up with init_rollback, like the other mrk scripts. Until 2026-09-27 it kept its own copy of an older check, which rewrote the file to a bare shebang whenever its first line was not exactly #!/usr/bin/env bash.
  • Handoff — Stops this Mac advertising its activity to nearby Apple devices, and stops it receiving theirs. The keys are ByHost, so harden writes them with defaults -currentHost.
  • Quarantine prompt — this step lowers the security floor. It sets LSQuarantine to false. macOS then does not show the "downloaded from the Internet" dialog on the first launch of an application. Gatekeeper still runs. The signature check and the notarization check are unchanged, and macOS still refuses an unsigned application. Only the extra confirmation goes away.

snapshot-prefs mrk

Caution
snapshot-prefs scans every staged file for API keys and tokens before it commits. If the scan finds a match, snapshot-prefs stops and asks you to confirm. It does not ask when NONINTERACTIVE=1 is set or when there is no terminal — in those two cases it aborts. Read the reported lines before you answer.

snapshot-prefs exports the app preferences and pushes them to the private mrk-prefs repository. It exports plists for 17 named applications, and every io.github.sevmorris.* domain but KeyVault's as a group. It also copies the Application Support files and the config directories, and keeps MusicBrainz Picard's settings with the credentials taken out.

The group export takes my own applications without naming them, because that list changes when I ship something new and a hand-written list would go out of date. Magic Backup Machine carried these preferences before 2026-09-02, inside an rsync mirror that keeps the current state and no history.

snapshot-prefs [--dry-run | -n] [--help | -h]
  • -n, --dry-run — Export into a scratch copy of ~/.mrk/preferences, and report the commit a real run would make: each file, and for a changed plist the keys that changed, besides the plists it would leave out. ~/.mrk/preferences is left as it was, and nothing is committed or pushed. The secret scan still runs, and says when the real run would stop to ask. make snapshot-prefs ARGS=-n runs it.
  • -h, --help — Show the usage summary and exit.
  • Apps: BetterSnapTool, Thaw, iTerm2, Raycast, Stats, Loopback, SoundSource, Audio Hijack, Farrago, Piezo, Typora, Keka, TimeMachineEditor, MacWhisper, Helium, Waves Central, MusicBrainz Picard. Descript was removed on 2026-09-17, because it is no longer installed; its saved plist stays in mrk-prefs. Thaw replaced Ice the same day, because Ice 0.11.12 crashes at launch on macOS 26.7. Ice's saved plist stays in mrk-prefs too, and Thaw's is saved from the first run after Thaw is set up.
  • Application Support: Loopback (devices and routing), SoundSource (presets and sources)
  • Config directories: Calibre (~/Library/Preferences/calibre/). Calibre keeps a tree of files, not a defaults domain, so snapshot-prefs copies the files.
  • Picard settings: config/picard/settings.ini. Picard writes its OAuth tokens into the same INI as its settings, ~/.config/MusicBrainz/Picard.ini, so snapshot-prefs does not copy that file. It keeps the [application], [setting], [profiles] and [plugin.*] sections, and leaves out [persist], which holds the tokens. It replaces the value of each key whose name marks a credential with <redacted>, so a diff still shows whether one is set. The copy is history, not a backup: post-install never restores it, and Magic Backup Machine keeps the real file. Until 2026-09-24 nothing was kept, and when the Cover Art Archive was found switched off after the Picard 3 betas, nothing could show when that had happened. The org.musicbrainz.Picard plist in the list above holds only macOS file-panel state.
  • snapshot-prefs converts each binary plist to xml1 before it scans the file, because the scan cannot read a binary plist.
  • The scan before the commit covers every staged file that carries content, fonts excepted. Until 2026-09-10 it skipped a renamed file: git add -A stages a plist whose name changed as a rename, and the list the scan read held only added and modified files, so a secret in it went unread.
  • snapshot-prefs records every git repository in ~/Projects that has an origin remote in repos.tsv, the manifest restore-repos clones from — including one kept a folder down, such as FloppyLetters/FloppyLetter2601, which it names by that path. The list is the one pushall sweeps. It warns about a repository with no origin, and it names the folders it cannot record because they are not repositories; until 2026-09-10 those were left out without a word.
  • snapshot-prefs refuses to start while a merge, rebase or cherry-pick in ~/.mrk/preferences is unfinished, or while a file there has unresolved conflicts, and exits 1. It checks before it exports anything. pull-prefs pulls with --ff-only, so only a git command run by hand leaves the repository in that state.
  • snapshot-prefs skips an app that is not installed, and it reports the skipped apps when it exits.
  • snapshot-prefs does not quit any app. defaults export asks the preferences system, which has an open app's changes as soon as it makes them — measured with a running test app whose change was visible to defaults export before the app had quit or synchronised. Until 2026-09-11 its help text, this page, the manual and SMAC-1 all said it quit each app first; it never had.
  • It reads each app's preferences where the app keeps them: ~/Library/Preferences/ID.plist when that file exists, and the app's sandbox container otherwise (prefs_source in scripts/lib.sh). Asked by bundle id alone, defaults prefers the container's copy whenever there is one, and a container outlives the sandboxed build that wrote it. Five of my own apps have one, and until 2026-09-11 snapshot-prefs saved those abandoned copies instead of the live settings — months out of date, and for JustIn and WaxOn missing their settings entirely.
  • An app with no preferences here yet is skipped, and the copy saved from before is kept. defaults export does not fail on an absent domain: it writes an empty dict, which replaced the saved copy and was pushed. BetterSnapTool reaches that state on a new Mac, because it comes from the App Store and is installed after mrk-post-install has run.
  • The group of my own apps is listed by defaults domains, so a sandboxed app's domain, which exists only in its container, is included. Empty domains are left out: ClipHack's tests leave one behind for each test process, and ten of them had been saved.
  • KeyVault is never exported. Its plist holds no secret, but it is a manifest of what the vault holds, and mrk-prefs must not carry one. KeyVault was never among the named applications, but from the 2026-09-02 migration until 2026-09-30 the group export took its domain with the rest, and seven snapshots pushed its note categories, last folder and window state. The group now leaves out each domain in OWN_APPS_EXCLUDED, KeyVault's alone, and deletes a copy it finds saved, so the next commit removes it; a dry run reports that removal. The copy was removed from mrk-prefs by hand the same day, and the old copies stay in its history.
  • Keys that change on their own. A plist that differs from the last commit only in the keys an app rewrites without anyone changing a setting is left out of the commit and put back as the last commit has it, and when nothing else changed there is no commit; it says which plists it left out. The keys are Sparkle's update-check times, window, split-view, menu bar item and file-panel positions, launch counters, the record of the versions that have run, and a short list per app — SoundSource's regenerated uuids, iTerm2's NoSync* state, Raycast's and Stats' update and analytics timestamps among them. The list is PREFS_NOISE in the script, taken from what changed in the sixty snapshots before 2026-09-30: 274 times a plist had changed in nothing else, and 12 of the sixty commits held nothing else. Values are compared as what they hold, so the same JSON, plist or archive written in a new order is no change. The export is not filtered: a plist with any other change is committed whole, these keys included. Without python3 every changed plist is committed, as before.
  • An unpushed commit. When a push fails, the commit stays in ~/.mrk/preferences. snapshot-prefs says that the commit is kept and that the next run pushes it, and exits with git's status. Until 2026-10-01 the run ended on git's own error, and nothing said what had become of the commit. The next run pushes that commit, also when it finds no changes to commit, and ends on "Pushed to". "No changes to push." thus means that mrk-prefs has the last commit. A dry run shows how many commits the real run would push. snapshot-prefs compares the branch with its upstream as of the last push, and does not ask the network. Until 2026-10-01 a run that found no changes stopped at "No changes to push." and exited 0, and the commit stayed on this Mac. From 2026-09-30 that was the usual run, because snapshot-prefs leaves out the keys above.
  • tests/snapshot-prefs.sh covers it; see ci-check.

status mrk

status is a two-pane TUI dashboard: the day's work first, then the installation. The same binary runs as mrk-status, and prints the same panels as text with --plain, which is what make status shows.

status
mrk-status [--plain | --help | -h]
  • --plain — Print the panels as text, each line with its fix, and exit 0. Colour only when stdout is a terminal.
  • Four panels, in this order, each with a ✓, ⚠, ✗ or · mark. Until 2026-09-30 the dashboard was the installation checks alone, which on a Mac set up months ago are green every day and say nothing about the day's work; they are now one panel, last.
  • Unrecorded — what the next Mac would not get. Homebrew packages installed but not in the Brewfile (make sync ARGS=-c), and Brewfile entries not installed, which it names with both repairs — make sync ARGS=-p if you removed them, make brew if they are not installed yet — and offers neither on f, since they are opposites. Both lists are sync --check, sync's own comparison, its ignore list included. Uncommitted changes and unpushed commits in ~/mrk (bin/mrk-push), and its untracked files, which mrk-push never commits. The repositories pushall sweeps, found by project_repos: uncommitted changes and unpushed commits (bin/pushall), and those with no upstream or with untracked files. The repositories repos.tsv does not record (make snapshot-prefs), and those with no origin remote, which nothing can record or push.
  • Upkeep — ~/mrk behind origin/main as of the last fetch, which check-updates makes once a day (make pull), when main is checked out. The Go tools older than their source, by tool_freshness, the check maintain makes (make build-tools). Outdated Homebrew packages, read with HOMEBREW_NO_AUTO_UPDATE=1 so the check never starts an update (make update). macOS updates for the installed major version, from macOS's own record of its last check, which costs no network (make updates). A major upgrade on offer is named and never counted, as macos-updates treats it. Only macOS itself can be a major upgrade. Safari and the Command Line Tools have versions ahead of macOS: 27.0 for both on macOS 26. make updates installs them, so the panel counts them as updates. Until 2026-10-01 it called them major upgrades that mrk never installs.
  • Time Machine Backups — read from /Library/Preferences/com.apple.TimeMachine.plist. ⚠ when there is no destination, which is how this Mac stood on 2026-09-30, or when automatic backups are off. Otherwise the last backup, the newest snapshot date its destinations record: ✓ within a day, ⚠ older than a day, ✗ older than seven days. It offers no fix, because a destination is chosen in System Settings. Only the no-destination case has been seen on this Mac; the dated ones are tested against fixtures.
  • Installation — the checks that were the whole dashboard, folded into one panel: dotfiles, ~/bin links, shell, PATH, Homebrew, the Brewfile (a count, its drift being under Unrecorded), macOS defaults, security hardening, and the files setup displaced, when there are any. Each has a line, and a check that warns or errs adds its problem lines and its fix.
  • Each line's fix is shown beside it. f runs the panel's first fix on a line that warns or errs, after you confirm it; a suggestion on a · line is never run. A panel takes the mark of its worst line that passes, warns or errs, and is · only when it holds nothing else, so an aside cannot turn a healthy panel grey.
  • Right pane — the lines of the selected panel.
  • f — Run the selected panel's fix.
  • r — Run all the checks again.
  • tab / ←→ — Move to the other pane.
  • Until 2026-09-10 mrk-status compared only its first argument against --help and -h and opened the dashboard on anything else, so an unrecognised flag was discarded. The same was true of mrk-menu. Both now exit 2.
  • The dotfiles check counts what mrk-setup links: regular files in dotfiles/, and no directory, documentation, example or .DS_Store. Until 2026-09-27 a dotfiles/.claude/ or .DS_Store counted as a dotfile.
  • make status runs scripts/status, which runs this checkout's bin/mrk-status --plain, reporting on that checkout, and is linked nowhere in ~/bin. Until 2026-09-30 scripts/status was a second implementation of the checks in bash, and the two kept parting in their failure branches, each having had a fix the other lacked. When brew list failed, make status listed all 128 Brewfile packages as not installed — the P-4 defect fixed here on 2026-09-09. And this dashboard offered the bare chsh that make status had stopped offering on 2026-09-10, for the reason in the next item. There is now one set of checks.
  • The Shell fix is chsh -s <zsh> only when that zsh is listed in /etc/shells. chsh refuses a shell that is not, and on a new Mac Homebrew's zsh is not: make all runs Phase 1 before Phase 2 installs it. Then the fix is make setup ARGS="--only shell", which registers the shell and sets it.
  • The Tools fix for a broken link is make fix-exec, which removes a link whose script is gone. Until 2026-09-11 it was make setup, which links only scripts that exist: pressing f re-ran all of Phase 1, left the link broken, and offered the same fix again. A test now runs the fix and requires the check to pass afterwards, because a fix command that merely exists passed the earlier gate.

Caution

mrk-push --dry-run      # change nothing

  • -- — End option parsing, so a commit message can begin with a dash.

That is the case in make all on a new Mac, which runs every phase with the PATH it started with. Until 2026-09-27 it stopped there with "Go is not installed" right after Phase 2 had installed Go.
  • The Makefile links the binaries into ~/bin only when it runs in the checkout that ~/bin serves: $MRK_ROOT, or ~/mrk when MRK_ROOT is not set. A build in any other checkout — a clone, a worktree, a scratch copy, a CI runner — makes the binaries and says that it did not link them. Until 2026-09-16 every build linked, so a make build-tools in a scratch copy pointed mrk-status, mrk-picker, mrk-menu and status at that copy.
  • The binaries are gitignored build artifacts, and nothing warns you on its own that one is older than its source: make maintain reports it, but only when you run it. Run build-tools after changing anything under tools/, or you keep using the previous binary.
  • The Makefile stamps each binary with the version and commit from git describe --tags. That is why the v1.0.0 tag is kept even though its GitHub release was deleted — without a tag the binaries report a bare commit SHA.

macos-updates mrk

macos-updates installs the macOS updates for the installed major version. It never installs a major upgrade, such as macOS 26 to macOS 27. make updates and step 3 of update-full run it.

macos-updates [-n | --dry-run] [--help | -h]
  • -n or --dry-run — List the updates that macos-updates would install, and the upgrades that it leaves alone. macos-updates installs nothing. Through Make, use make updates ARGS=-n.
  • macos-updates runs softwareupdate --list, then gives softwareupdate --install the label of each update to install. It never uses --all.
  • An update is a macOS update when its label or its title contains "macOS". macos-updates installs a macOS update only when the first number of its version is the same as that of the installed version. It names every other macOS update as a major upgrade, and leaves it alone. No option of macos-updates installs a major upgrade: install one yourself, from System Settings > General > Software Update.
  • macos-updates installs every other update in the list, for example Safari and the Command Line Tools. Their version numbers can be ahead of the operating system: on macOS 26, both are at 27.0.
  • When macos-updates cannot read an entry in the list, it installs nothing and exits with status 1. It does the same when softwareupdate --list fails, or prints output that macos-updates does not recognise. If Apple changes the format of the list, the run stops; it does not install an update that it cannot identify.
  • macos-updates exits 0 when it installs the updates that it selected, and when there is nothing to install. It exits 1 when softwareupdate fails, and 2 on a wrong command line.
  • macos-updates does not restart the Mac. softwareupdate says when an update needs a restart, and update-full offers one at the end.
  • macos-updates runs under the bash 3.2 that macOS supplies, so make updates works on a new Mac before Homebrew is installed.
  • Until 2026-09-16, make updates ran softwareupdate -ia. The -a option installs every update that Apple lists, and Apple lists the next major version as a recommended update. On 2026-09-15, on macOS 26.7, macOS 27 was the only update in the list, and softwareupdate started a 26 GB download of it without a password prompt. The download belongs to the softwareupdated service, so it continued after the command stopped, until it was cancelled in System Settings. tests/macos-updates.sh now runs macos-updates against that list.
Caution
To stop softwareupdate does not stop a download that it started. To cancel the download, use System Settings > General > Software Update.

install-apps mrk

install-apps installs the applications published from their owner’s own GitHub repositories. make apps runs it, and mrk-post-install sources it and runs the same list as part of Phase 3. It was extracted from post-install on 2026-09-17 so that both share one copy of the installer and one copy of the list.

install-apps [--help | -h]
  • The list is COMPANION_APPS in scripts/install-apps, one line per app: bundle name, the repository holding the releases, and a display name. As of 2026-09-17 it is Barkeep, ClipHack, DoublEnder, FilmStrip, KeyVault, Magic Backup Machine and WaxOn/WaxOff.
  • It installs, it does not update. An app already in /Applications is skipped. mrk bootstraps a Mac; each of these apps checks GitHub for its own updates once it is running. To replace one, delete it and run make apps.
  • Nothing reaches /Applications unverified. The app inside the downloaded DMG must verify with codesign --verify --deep --strict, carry the team identifier in GITHUB_APP_TEAM_ID, and be accepted by spctl --assess — which for a Developer ID app means notarized. It is checked again after the copy. A copy that fails, or that Ctrl-C cuts short, is removed, so the next run does not take the remains for an installed app. Until 2026-09-28 only a failed copy was removed: an interrupt detached the image and deleted the temporary files, but left the partial app, and the next run's skip test kept it. Run on its own, install-apps now exits on Ctrl-C as mrk-post-install does, which lets that cleanup run. curl sets no quarantine attribute, so Gatekeeper never assesses an app installed this way on its own.
  • The bundle inside the DMG must be named exactly as the list says. A DMG holding a differently named app is refused rather than installed under the wrong name.
  • The download prefers gh when it is installed and authenticated, and falls back to curl against the public API. A private repository needs the gh path: an unauthenticated request for a release in one returns 404, which is indistinguishable from “no such release”. sevmorris/magic-backup-machine is private, and before this fallback existed it could not be installed at all.
  • ClipHack’s DMGs are published to a separate repository, sevmorris/ClipHack-releases; its source repository carries no release assets.
  • One app failing never stops the rest. install-apps exits 1 when any app failed to install, and 0 when every app is present or skipped.
  • A private repository without a logged-in gh is a skip, not a failure. When the unauthenticated API answers 404, install-apps names the app, says to run gh auth login and then make apps, and does not count it. Any other answer is still a failure: a rate limit (403), no network, a DMG that does not download. Until 2026-09-28 the 404 counted, so on a new Mac, before gh was logged in, Magic Backup Machine made mrk-post-install exit 1 and make all stop before build-tools. tests/install-apps.sh covers it; see ci-check.
  • Two of the owner’s apps are absent, both retired. Cypher/FL2601 (2026-09-23) never came from here: sandboxed with no network entitlement, it could not check for its own updates, so it was a Homebrew cask. WireHack is superseded by ClipHack.

defaults-watch mrk

defaults-watch names the preference key that a change in System Settings writes. It snapshots every preferences domain, waits while you change one setting, snapshots again, and prints each key that changed, with its old and new value and what scripts/defaults.sh needs to keep it. It changes nothing.

defaults-watch [--seconds N]
  • --seconds N — Wait N seconds between the snapshots instead of for Return. Without it defaults-watch needs a terminal, and exits 2 with none.
  • -h, --help — Show the usage summary and exit.
  • Until 2026-09-30 a setting changed in System Settings was the one change no mrk command recorded, and finding its key meant guessing a domain for defaults read.
  • It watches your domains — NSGlobalDomain and every one defaults domains lists — through defaults export, which asks the preferences system and so sees a change before it reaches the file. It watches the domains for this Mac alone, -currentHost, the same way, and the readable files in /Library/Preferences, which hold settings for all users. On this Mac that is about 740 domains, exported eight at a time; a snapshot takes about two seconds.
  • For a key defaults.sh writes, it names the line and says whether the new value is the one mrk sets, or prints the line to change it to. For any other key it prints the write_default line to add, quoted the way defaults.sh quotes, and names the description check-defaults-desc will then want in docs/defaults/script.js. It reads the trackpad loop's "$domain" as each domain the loop names.
  • What write_default cannot write it says so about: a -currentHost key, with the defaults -currentHost write line hardening.sh uses for its one; a key for all users, with the sudo defaults write line; a dictionary or an array, with the path to what changed inside it; and a key that was deleted, with the defaults delete that would remove it.
  • Window, split-view, menu bar item and file-panel positions, update-check times, launch counters and any date are listed apart, as probably not the setting: the kinds of key snapshot-prefs leaves out of a commit. A setting that is not a preference — a login item, a network or account setting, a privacy permission — is stored elsewhere, and it says so when nothing else changed.
  • When defaults domains fails it exits 1, and never reports that nothing changed. tests/defaults-watch.sh covers it; see ci-check.
