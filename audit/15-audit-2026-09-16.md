# Module 15 — mrk on the new Mac, on a newer macOS (2026-09-16)

**Date:** 2026-09-16, finished 2026-09-17
**Machine:** MacBook Pro 16-inch, Apple M5 Pro (`Mac17,8`), macOS 26.7 (`25G229`), migrated
from the previous Mac on 2026-09-15. The old Mac ran macOS 15, the release the manual named as
mrk's platform until this module.
**Scope:** two requests. First, `update --full` had started a macOS 27 upgrade, which is never
wanted: fix that. Second, a full audit of mrk as it runs on this Mac.
**Baseline:** `6a38545` (PR #7). Module 14 was the last full pass (2026-09-09, `c460f02`). Its
findings are closed and were not re-examined.
**Method:** run what can run. That means the read-only and dry-run paths of every command
(`make status`, `mrk-status` in a pty, `doctor`, `setup --dry-run`, `trim-services -n`,
`maintain --dry-run`, `restore-repos -n`, `snapshot-keys -n`, `clean-ds --dry-run`,
`macos-updates`), `ci-check` on a clean clone, and each command's claims checked against the
live system (`/var/log/install.log`, `launchctl print-disabled`, `defaults`, `tmutil`, Finder's
scripting dictionary). A command that is destructive, or that raises a permission prompt, was
read rather than run; the list is at the end.

**Headline: on this Mac the danger came from a macOS change, not a code change.** `make
updates` had run `softwareupdate -ia` unchanged since the first commit. On macOS 26.7 in
September 2026, Apple listed macOS 27 as the only update, marked Recommended, and `-a` installs
every listed update. Nothing in mrk broke. The environment changed around a line that had
always meant "install everything". Audit 02 had named this risk ("installs ALL pending macOS
updates including OS version upgrades") and left it as a blast-radius note.

**Second headline: several claims were true on the old Mac and are not true here.**
`trim-services` promised a disable survives a restart, and on this Mac neither Photos agent is
disabled. The Software Update keys in `make defaults` are reported as applied, and the service
that owns them does not read them. `hide_tm.sh` asks Finder for a property Finder does not have.
The Safari settings were skipped at the migration, and the only notice was one log line. None of
these fails a gate. They were found by asking the system what it holds.

## T-1 — `make updates` and `update-full` installed any listed update (HIGH, FIXED)

`Makefile` `updates:` was `@softwareupdate -ia || true`. `bin/update-full` step 3 ran
`make updates`, or `sudo softwareupdate -ia` when `~/mrk` was not a repository. `-a` means
"all appropriate updates", and on this Mac that was one update:

```
$ softwareupdate --list
* Label: macOS 27-26A428
	Title: macOS 27, Version: 27, Size: 11728377KiB, Recommended: YES, Action: restart,
```

**What happened, from `/var/log/install.log`.** The user ran `update --full`. The log records
the command it ran, from `/bin/bash`, the shell the `updates` recipe runs in:

| Time (2026-09-15) | Event |
|---|---|
| 21:46:24 | `softwareupdate -ia` starts. The scan finds `MSU_UPDATE_26A428_patch_27.0_major` and no minor update |
| 21:46:31 | "Non-interactive authorization succeeded". No password was asked for. The download starts |
| 21:59:04 | The `softwareupdate` client disconnects: the command has ended |
| 21:59:40 | System Settings opens and shows the download still running: 13,599,729,229 of 26,464,573,437 bytes |
| 21:59:42 | "Canceling in-progress updates" — cancelled in System Settings |
| 22:02:53 | "User turned off automatic downloads" |

**The download outlived the command.** It belongs to `softwareupdated`, so stopping
`softwareupdate` does not stop it. The fix therefore cannot be "interrupt it in time". The
upgrade must never be requested.

**Nothing is staged.** Every `SUOSULoginCredentialPolicyManager` line since 21:59:46 says "No
update downloaded and prepared", the latest at 2026-09-17 01:04:26. The system
`AutomaticDownload` is `0`. macOS 27 remains listed and is not downloading.

**Fix.** A new command, `bin/macos-updates`. It runs `softwareupdate --list`, parses the
two-line entries, and gives `softwareupdate --install` the labels of the updates to install.
An update is macOS itself when its label or title contains "macOS". A macOS update is installed
only when the first number of its version equals the installed major version from `sw_vers`.
Every other macOS entry is named as a major upgrade and left alone. Safari and the Command Line
Tools install normally, although their versions (27.0) run ahead of the OS. The command fails
closed: an entry it cannot parse, a macOS entry whose version does not parse, a failed `--list`,
or output with neither a label nor "No new software available" stops the run before anything
is installed, with exit 1. No option installs a major upgrade. It is bash-3.2-clean, with no
bash-4 re-exec, so `make updates` still works on a new Mac before Homebrew is installed.

- `Makefile:118-119` — `updates:` runs `"$(BIN_DIR)/macos-updates" $(ARGS)`, without
  `|| true`. A real failure now exits non-zero, which also closes audit 04's M2.
- `bin/update-full:217-223` — step 3 runs `"$SCRIPT_DIR/macos-updates"`. The `sudo -ia`
  fallback is gone. The prompt text and `--help` say "never a major upgrade".
- `tools/mrk-menu/data.go` — the `make updates` row says so, and a new row runs
  `make updates ARGS=-n`.

**Test.** `tests/macos-updates.sh`, run by `ci-check`, puts stubs of `softwareupdate` and
`sw_vers` first on PATH, refuses to run if they are not, and runs 18 cases under `/bin/bash`
3.2.57 and Homebrew bash 5.3.20. The first fixture is the listing above, verbatim. The cases
cover: a minor update beside the upgrade (only the minor one; its label with spaces arrives as
one argument), Safari and the CLT at 27.0, a security response `26.7.1 (a)`, a macOS 27 host
(27.0.1 installs, 28 does not), nothing listed, `--dry-run` and `-n`, a failed `--list`, an entry
with no title line, an unparseable version, unrecognised output, a failed install, `--help`,
an unknown option, and an unreadable `sw_vers`. Four repository checks run once per test run:
no tracked script calls `softwareupdate` with `-a`/`--all` (comment lines excepted); topgrade's
`system` step stays disabled; `make -n updates` runs `macos-updates`; update-full calls it.

**Mutation check.** Six broken variants, each run against a scratch copy. Every one failed the
test:

| Mutation | Failing checks |
|---|---|
| `is_macos` never matches (install everything) | 12 |
| major-version comparison always true | 10 |
| unreadable entries ignored | 4 |
| `Makefile` back to `softwareupdate -ia` | 2 |
| update-full calls `softwareupdate -ia` directly | 2 |
| topgrade `system` step re-enabled | 1 |

**Live.** `bin/macos-updates --dry-run`, `make updates ARGS=-n`, and then `bin/macos-updates`
for real (17:53) printed "Not installing macOS 27 (27): it is a major upgrade, and mrk never
installs one." and exited 0. The install log for that run shows one `--list` call, and no
authorization or install.

**Docs.** BIN-1 §2.37 (new), §2.30 and §2.22. `manual.md`: the `update-full` and `make updates`
rows, and a Caution beside `update-full`. README. SMAC-1 Tables 2.7-1 and 2.7-2, and the

## T-2 — A build in any checkout repointed `~/bin` at that checkout (MEDIUM, FIXED)

Found by causing it. While testing T-1, `make build-tools` ran in a scratch copy under the
session's temporary directory. `link-home-bin` always wrote to `$(HOME)/bin`, so at 17:56
`~/bin/mrk-status`, `mrk-picker`, `mrk-menu` and `status` pointed into the scratch copy.
`make setup-dry` then reported "Would link" for all three. They were repointed at `~/mrk/bin`
at 17:58, and no other link pointed outside the repository. Left in place, they would have
dangled once the scratch directory was deleted, and stayed that way: `fix-exec` removes only a
dead link that points *into* the repository, so it would not have pruned them either.
`status`, `mrk-status`, `mrk-menu` and `mrk-picker` would have failed until the next
`make build-tools` in `~/mrk`.

Any build in another checkout does this: a clone, a worktree, `make ci` run to test a branch.
CI builds too, harmlessly, on a runner with no `~/bin` to speak of.

**Fix.** `Makefile:9-27`. `link-home-bin` links only when `REPO_ROOT` resolves (`pwd -P`) to the
same directory as `$MRK_ROOT`, or `~/mrk` when that is unset. `update-full`, `mrk-menu` and
`mrk-status` read the same variable. Anywhere else it prints "built, not linked: ~/bin serves …,
not this checkout". The macro now takes the link names, so `status` goes through the same guard,
and it prints its own ✓ line only when it has linked. The scratch-copy build at the end of this
module is the regression run: see "Final gates".

**Verified** with a probe makefile that calls the macro against a throwaway `HOME`:

| Layout | Result |
|---|---|
| no `~/mrk` | not linked |
| `~/mrk` a symlink to this checkout | linked, to `/Users/sev/mrk/bin/mrk-picker` |
| `~/mrk` another directory | not linked |
| `MRK_ROOT` = this checkout | linked |
| `MRK_ROOT` = elsewhere | not linked |

`make setup` is not changed. It links whichever checkout it runs from, and that is its purpose.

## T-3 — The Software Update keys in `make defaults` change nothing (MEDIUM, decision)

`scripts/defaults.sh:393-412` writes seven keys with `write_default`, which calls
`defaults write <domain>`, and that is the **user** domain:

```
com.apple.SoftwareUpdate  AutomaticCheckEnabled, AutomaticDownload, ConfigDataInstall,
                          CriticalUpdateInstall, ScheduleFrequency
com.apple.commerce        AutoUpdate, AutoUpdateRestartRequired
```

`softwareupdated` takes these settings from `/Library/Preferences/com.apple.SoftwareUpdate.plist`,
and the user-domain copy does not govern it. The evidence here is direct.
`~/Library/Preferences/com.apple.SoftwareUpdate.plist` says `AutomaticDownload = 1`, and at
02:49, 08:28 and 14:27 on 2026-09-16 the daemon logged "autoDownload=NO", the value in the
system file. `AutoUpdateRestartRequired` is the key that macOS 10.13 and earlier used for
"Install macOS updates"; later releases use `AutomaticallyInstallMacOSUpdates`, in the system
domain. On this Mac all seven keys are inert. `make status` and
`mrk-status` still count their seven undo lines toward "Defaults have been applied", and MRK-1
describes each one as if it took effect.

**Why this is not fixed here.** The obvious repair is `sudo defaults write
/Library/Preferences/…`, and that would turn `AutomaticDownload` back on. That setting was
turned off in System Settings at 22:02 on 2026-09-15, while the macOS 27 download was being
cancelled. With it on, `softwareupdated` may download a major upgrade in the background. This
module did not test whether it would; T-1 does not cover it. Which Software Update settings mrk
should own is the owner's decision. The security-relevant ones are at their system defaults
already: the daemon logs `autoConfigData=YES, autoCriticalInstall=YES`.

**Recommendation.** Delete the seven lines and their MRK-1 descriptions, and leave Software
Update to System Settings. `check-defaults-desc` enforces both directions, so the two edits have
to land together. The key count in README and `manual.md` falls from 143 to 136.

## T-5 — trim-services could not tell whether a disable held (LOW; tool FIXED, state open)

`~/.mrk/services-rollback.sh` (12:46, 2026-09-15) holds undo lines for `photoanalysisd` and
`mediaanalysisd`. On 2026-09-16, `launchctl print-disabled gui/501` and
`/private/var/db/com.apple.xpc.launchd/disabled.501.plist` listed neither agent, and
`photoanalysisd` was running (pid 845). The Mac had restarted at 14:23 on 2026-09-15 and at
07:39 on 2026-09-16. The same file does keep other disables across those restarts (Siri,
FolderActionsDispatcher, ScriptMenuApp), so launchd's override store itself persists.

Whether the disable failed on 2026-09-15 or was dropped later is **not known**, and trim-services
could not have said. It writes the undo lines *before* `launchctl disable`, so their presence
proves nothing. It judged success from `launchctl`'s exit status alone, and then printed "A
disabled job stays disabled across a reboot". Its dry run offered to disable jobs without
checking whether they already were. The "enabled" rows the undo script would have left are
absent, so the undo did not run.

**Fix.** `scripts/trim-services:73-90, 102-106, 133-138`. It reads `print-disabled` once, and a
job already listed is reported as "already disabled". After each `launchctl disable` it reads the
list again, and reports the job as disabled only if the list now has it. Otherwise it warns that
"launchctl accepted the disable, but launchd does not list … as disabled". The closing lines
count the already-disabled jobs, and ask for a check after the next restart instead of promising
the result. The label is matched as a fixed string, for both `=> disabled` (macOS 26) and
`=> true` (older).

**Verified** against a stubbed `launchctl` and a throwaway `HOME`. Dry run with one agent already
disabled: "already disabled" for that one, "Would disable" for the other two. Real run where the
disable does not stick: three warnings, "Disabled 0". Real run where it sticks: three disabled,
and the stub store holds all three. Second real run: "3 already disabled". Live dry run on this
Mac: "Would disable 3 service(s); 0 already disabled; 2 not loaded".

**Open.** If the two Photos agents should be off, run `trim-services` again. After the next
restart, check with `launchctl print-disabled gui/$(id -u)`. If they come back, macOS 26.7 is
undoing the disable, and the entries should say so or go.

## T-9 — `hide_tm.sh` probably hides nothing; there is no Time Machine destination (LOW, decision)

`bin/hide_tm.sh` tells Finder `set visible of disk … to false`. The scripting dictionary of
macOS 26.7's Finder (`sdef /System/Library/CoreServices/Finder.app`) gives `disk` → `container`
→ `item` no `visible` property. Only `application`, `column`, `process` and `window` have one.
The script re-raises the resulting error (F-28, `d9dbd82`), prints a warning per volume, and
exits 0. For a name that is not mounted it does nothing, silently. **Not executed:** running it
needs Automation access to Finder, which would have raised a consent prompt, so this rests on the
dictionary alone.

Separately, **`tmutil destinationinfo` reports "No destinations configured"**. Nothing in mrk,
the manual or sevmac sets up Time Machine or reports its absence. The restored TimeMachineEditor
preferences schedule backups that have nowhere to go. Step 7 of the manual's migration list
names Time Machine as the only other place a copy of `~/Projects` might be. On this Mac there is
no such copy.

**Docs.** A Caution in BIN-1 §2.5, and a note on the `hide_tm.sh` rows in `manual.md` and SMAC-1
Table 2.7-2.

**Recommendation.** Configure Time Machine. Then either delete `hide_tm.sh` (with its BIN-1,
manual and SMAC-1 rows) or rewrite it against a mounted TM volume, where it can be tested.

## T-12 — Xcode 27's SDK is newer than the OS (INFO, handled elsewhere)

`pyenv exec python` runs a subprocess, with `MACOSX_DEPLOYMENT_TARGET` 26.7. The Go tools build and pass their tests with
