## Y-1 — `git local-branches` lists branches that have an upstream (LOW)

`dotfiles/.gitconfig:14`:

```
local-branches = !git branch -vv | cut -c 3- | awk '$3 !~/\\[/ { print $1 }'
```

It parses `git branch -vv` as text. `.gitconfig:17-25` sets `color.ui = always`, and
`branch = always` with it, so git writes escape codes into the pipe as well as to a terminal.
The codes split and shift the fields that awk reads.

Reproduced in a scratch repository with the owner's `~/.gitconfig`. `master` tracks
`origin/main`, and `feature` has no upstream:

```
truth (for-each-ref, no upstream):      feature
git local-branches:                     ^[[33mfeature^[[m
                                        ^[[7;33mmaster
git -c color.branch=never local-branches:  feature
```

The alias names a branch that has an upstream. It also wraps every name in escape codes, so
its output cannot be passed to another git command, which is the point of a list of branch
names. In `~/mrk` it prints `main`, and the right answer is nothing.

The same `[color]` block holds more cruft:
- `branch`, `diff`, `grep` and `interactive = always` repeat `ui = always`.
- `status` and `showbranch = auto` contradict it.
- `pager = true` is git's default.
- `[push] default = simple` (`:4-5`) is git's default since 2.0.

Nothing in mrk parses coloured git output. Every pipe of `git branch`, `log`, `diff`, `show` or
`grep` in `scripts/`, `bin/`, the Makefile, `assets/` and the skills uses `--format`,
`--porcelain`, `--name-only`, `--quiet` or `rev-list`, or only displays the output. The
risk is in the owner's own pipes, and in sessions that run git through a pipe: this audit's
first `git grep` and `git log -p` output came back with escape codes in it.

**Fix.** `ui = auto` alone gives colour in a terminal and in git's own pager, and none in a pipe.
Delete the other seven lines. Optionally, rewrite the alias on `for-each-ref`, which does not
depend on colour.

## Y-2 — A topgrade pre-command cleans a Node install this Mac has never had (LOW)

`assets/topgrade.toml:23-26`, run before every `make update`, `update` and `update-full`:

```toml
"Clean Node global shims" = "bash -lc 'bp=$(brew --prefix 2>/dev/null) && rm -f \"$bp\"/bin/{yarn,pnpm,corepack} && rm -rf \"$bp\"/lib/node_modules/{yarn,pnpm,corepack}'"
```

Its comment says corepack, yarn and pnpm put shims into Homebrew's `bin/`. They do that for a
Node that Homebrew installed. On this Mac:
- Node comes from nvm (`~/.nvm/versions/node/v24.21.0/bin/node`, and pnpm beside it).
- No `node` formula is installed, and nothing installed depends on one.
- `brew "node"` was never in this repository's Brewfile (`git log -S`). The step came in with the
  first commit, merged from mrk1 and mrk2.
- `/opt/homebrew/bin/{yarn,pnpm,corepack}` and `/opt/homebrew/lib/node_modules` do not exist.

The step removes nothing on each run. Nothing documents it, and no test runs it. It is an
`rm -rf` in the Homebrew prefix, kept for a layout that has gone.

In the same file, `:6-12`: the comment explains three of the six disabled steps. `mas` is
disabled, and mas is not installed. mrk stopped using it on 2026-09-11. That entry is harmless,
and it is cheap to keep in case mas is installed again.

**Fix.** Delete the `[pre_commands]` section. Optionally, give the other three disabled steps
a reason in the comment.

## Decisions

### D-1 — Browser extension lists can never reach a new Mac

post-install opens the URLs in `assets/browsers/{safari,chrome,brave}-extensions.txt`
(`post-install:500-540`). `.gitignore:38` keeps those files out of the repository, and
`snapshot-prefs` does not save them to mrk-prefs. On a new Mac, `make all` runs from a fresh
clone, so no list exists, and the feature does nothing. This Mac has no list either. The three
`.txt.example` files have not changed since the first commit, and their examples include a
1Password extension, a cask the Brewfile no longer has.

Options:
- move the lists to `~/.mrk/preferences/` (mrk-prefs), where they travel, and read them from
  there
- remove the feature: the three example files, the three blocks in post-install,
  `open_extension_urls`, the ignore rule and SMAC-1's sentence (`index.html:667`)

### D-2 — History in BIN-1, and an STE record that nothing links to

BIN-1 has 131 sentences that begin "Until 2026-…". By a rough count, 165 sentences, about 3,500
of its 24,000 words (15%), say what a command used to do. The manual's share is 5%. Each one is
true, and some are worth keeping, but a command reference where one word in seven describes
the past is hard to use.

The defaults reference already solved this. The STE record (`docs/STE-CONVERSION.md`,
deviation 1) moved its history into a `background` field, shown in a labelled block. The same
split would suit BIN-1.

This is not X-15 again. X-15 asked whether to rewrite the older text in STE, and the owner chose
to leave it as it is. This asks where text about past behaviour belongs, and it applies to new
text as much as to old.

Separately, nothing links to `docs/STE-CONVERSION.md`. CLAUDE.md, the README and the manual do
not, and since X-15 its rules are the target for new text. A session that writes docs finds it
only by reading `audit/`. One line in CLAUDE.md would fix that.
