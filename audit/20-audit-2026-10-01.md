## X-1 — snapshot-prefs says "No changes to push" with a commit unpushed (MEDIUM)

`scripts/snapshot-prefs:757-760`:

```bash
if git diff --cached --quiet; then
  log "No changes to push."
  exit 0
fi
```

The script commits at `:821` and pushes at `:824`. When the push fails (no network, a locked
SSH agent), the run exits with git's status, and the commit stays in `~/.mrk/preferences`. The
next run exports again. When it finds nothing new to stage, it stops at `:758`, before any push.
It never asks whether the last commit reached mrk-prefs.

The exit at `:758` is older than this range. What changed is how often a run takes it. Until
#64 (2026-09-30) most runs found a Sparkle timestamp or a window frame, committed it, and the
push carried the earlier commit with it. #64 leaves those keys out (`:749-755`), so a run that
finds only them now stops at `:758`. By #64's own count, 12 of the last 60 snapshots held
nothing else.

Reproduced with the harness of `tests/snapshot-prefs.sh`: a scratch bare repository as
mrk-prefs, a stub `defaults`, a throwaway HOME.

```
run 1 (first snapshot):              exit 0,   origin commits: 1, "Pushed to …"
run 2 (theme changed, origin down):  exit 128, git: "…and the repository exists."
   local commits: 2, origin commits: 1, status: ## master...origin/master [ahead 1]
run 3 (origin back, only noise):     exit 0,   "No changes to push."
   local commits: 2, origin commits: 1, status: ## master...origin/master [ahead 1]
   pushed theme: dark   (this Mac's is: light)
run 4 (nothing changed):             exit 0,   "No changes to push."   origin commits: 1
```

**Why it matters.** mrk-prefs is what the next Mac restores from.
- The migration checklists tell the owner to read this output. `docs/manual.md:497` says "Check
  that the push succeeded: the output ends with 'Pushed to …'". SMAC-1 §2.6 step 4 says the same.
  Neither says what "No changes to push." means, and after #64 that is the usual last line.
- Nothing else looks. The dashboard's Unrecorded panel reads the git state of `~/mrk` and of
  each repository in `~/Projects` (`tools/mrk-status/daily.go:348-440`). Of `~/.mrk/preferences`
  it reads only the manifest.
- `nuke-mrk` does stop on unpushed work there. A Mac erased any other way gets no such stop.

**Suggested fix.** Before the "No changes" exit, compare HEAD with its upstream. When commits
are unpushed, or the branch has no upstream, push them and say so; when the push fails, exit
non-zero. A dry run reports the count and pushes nothing. The manual and SMAC-1 then say which
two last lines mean the remote is current.

## X-2 — One byte that is not UTF-8 makes the verdict say the run stopped short (MEDIUM)

`scripts/lib.sh:616`:

```bash
found=$(sed -e $'s/\x1b\\[[0-9;?]*[A-Za-z]//g' -e $'s/\x1b][^\x07]*\x07//g' "$log" 2>/dev/null | tr -d '\r' | awk '
```

macOS's `sed` stops at the first byte sequence that is not valid in the locale: "RE error:
illegal byte sequence". The `2>/dev/null` hides the message. `awk` then sees only the lines
before that byte, finds no Summary, and `topgrade_verdict` takes its no-summary branch.

This Mac's shells run with `LANG=en_US.UTF-8`. Reproduced with a transcript in topgrade's own
form, one Latin-1 byte in a download line above the Summary, and `/usr/bin/sed`:

```
== LC_ALL=C
  ⚠ Update finished: every step ran. 1 of 2 failed: Brew Cask (ARM).
== LC_ALL=en_US.UTF-8
  ⚠ topgrade stopped before its summary (exit 1): not every step ran. Its last output is above.
```

**Why it matters.** "Not every step ran" is the one sentence the function's comment says must
never be wrong in the other direction, and #71 was a whole PR to stop this same false sentence
from another cause. The recording holds the output of every package manager topgrade runs. One
file name in another encoding, anywhere in a run, is enough. With exit 0 the no-summary branch
prints nothing, so the "all N steps succeeded" line is lost without a word.

**Suggested fix.** Run the three filters under `LC_ALL=C`. The patterns are byte strings, and
the same run above shows they match in the C locale. Keep the `2>/dev/null` only on the read of
the file.

## X-3 — The dashboard calls a Safari update a major upgrade (MEDIUM)

`tools/mrk-status/daily.go:556-566` sorts every entry of `RecommendedUpdates` by one test: the
major number of its `Display Version` against the installed macOS.

`bin/macos-updates:84-94` applies that test only to macOS itself, and says why:

> The version test that follows cannot be applied to everything: Safari and the Command Line
> Tools carry version numbers ahead of the OS — 27.0 for both on macOS 26 — and are not upgrades.

So the range holds two copies of the rule, and the newer one (#66) lacks the half the older one
was written around. A probe test on a scratch copy, with the fixtures `daily_test.go` uses
(macOS 26.0.1 installed; Safari 27.0 and Command Line Tools 27.0 on offer):

```
sev=OK   "No macOS update for macOS 26"
sev=info "  offered, and never installed by mrk, being a major upgrade: Safari, Command Line Tools for Xcode"
```

Both lines are false. `make updates` installs both updates, and the panel offers no
`make updates` fix because it counts nothing. `TestUpkeepMacOSUpdates` has only macOS entries, so
it passes.

BIN-1 (`docs/bin/mrk-usage.html:762`), the manual and SMAC-1 §2.8 all say the panel treats a
major upgrade "as macos-updates treats it". On this Mac today the only entry is macOS 27.0.1, so
the panel is right today.

**Suggested fix.** Apply the version test only to an entry whose name or identifier says macOS,
as `is_macos` does. Count every other entry as an update `make updates` installs. Add the Safari
and Command Line Tools case to the Go test.

### lib.sh, update-full

- **X-4 (reproduced).** `run_topgrade` (`scripts/lib.sh:661-676`) removes its recording on the
  last line, with no trap. Away from a terminal it runs `topgrade | tee`, and a signal to the
  process group ends the shell before the `rm`. `make update </dev/null` in its own session,
  with a stub topgrade that sleeps:

  ```
  SIGINT  exit -2  left in TMPDIR: ['mrk.9bwEL6']
  SIGTERM exit -15 left in TMPDIR: ['mrk.xFcjp1']
  SIGHUP  exit -1  left in TMPDIR: ['mrk.PHiSjn']
  ```

  Each file holds the run's output so far. At a terminal the path is sound: Ctrl-C reaches
  topgrade through `script`, the verdict says "stopped before its summary (exit 2)", and the
  file is removed; a closed window leaves nothing either. The usual way in is
  `make update | tee log`, where stdout is not a terminal.
  → Fix: remove the file from a trap set for the length of the run, and restore the caller's
  traps after it.

- **X-8 (reproduced).** `bin/update-full:40-42` sources `scripts/lib.sh`, then
  `bin/lib/common.sh`. Both define `ok`, `warn`, `err` and `info`, and the second wins.
  `topgrade_verdict` is written for `lib.sh`'s `info`, an indented line on stderr. Under
  `common.sh` its `info` is a `→` line on stdout. In update-full the verdict's first line goes to
  stderr and its two continuation lines to stdout:

  ```
  $ update-full 2>/dev/null     (the verdict, as far as stdout shows it)
  → Nothing was interrupted: the other 1 succeeded, and the clean-up command after them ran.
  → The exit status is 1 for the failed step alone.
  ```

  `bin/maintain:37-39` sources both the same way, for `tool_freshness`, which prints through
  neither. The headers of the two libraries still state the rule this breaks: `lib.sh:4` says
  "standalone bin/ tools use bin/lib/common.sh", and `common.sh:4` the reverse. Four `bin/`
  tools source `lib.sh` now: mrk-push, pushall, maintain and update-full.
  → Fix: have `topgrade_verdict` print through its own `printf` lines to stderr, so it reads the
  same from every caller. Correct the two headers to say what is true.
