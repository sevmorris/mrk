## X-1 — snapshot-prefs says "No changes to push" with a commit unpushed (MEDIUM, FIXED)

`scripts/snapshot-prefs:757-760`:

```bash
if git diff --cached --quiet; then
  log "No changes to push."
  exit 0
fi
```

The script commits at `:821` and pushes at `:824`. When the push fails (no network, a locked
SSH agent), the run exits with git's status, and the commit stays in `~/.mrk/preferences`. The
next run exports again. When it finds nothing new to stage, it stops at `:758`, before any push.
It never asks whether the last commit reached mrk-prefs.

The exit at `:758` is older than this range. What changed is how often a run takes it. Until
#64 (2026-09-30) most runs found a Sparkle timestamp or a window frame, committed it, and the
push carried the earlier commit with it. #64 leaves those keys out (`:749-755`), so a run that
finds only them now stops at `:758`. By #64's own count, 12 of the last 60 snapshots held
nothing else.

Reproduced with the harness of `tests/snapshot-prefs.sh`: a scratch bare repository as
mrk-prefs, a stub `defaults`, a throwaway HOME.

```
run 1 (first snapshot):              exit 0,   origin commits: 1, "Pushed to …"
run 2 (theme changed, origin down):  exit 128, git: "…and the repository exists."
   local commits: 2, origin commits: 1, status: ## master...origin/master [ahead 1]
run 3 (origin back, only noise):     exit 0,   "No changes to push."
   local commits: 2, origin commits: 1, status: ## master...origin/master [ahead 1]
   pushed theme: dark   (this Mac's is: light)
run 4 (nothing changed):             exit 0,   "No changes to push."   origin commits: 1
```

**Why it matters.** mrk-prefs is what the next Mac restores from.
- The migration checklists tell the owner to read this output. `docs/manual.md:497` says "Check
  that the push succeeded: the output ends with 'Pushed to …'". SMAC-1 §2.6 step 4 says the same.
  Neither says what "No changes to push." means, and after #64 that is the usual last line.
- Nothing else looks. The dashboard's Unrecorded panel reads the git state of `~/mrk` and of
  each repository in `~/Projects` (`tools/mrk-status/daily.go:348-440`). Of `~/.mrk/preferences`
  it reads only the manifest.
- `nuke-mrk` does stop on unpushed work there. A Mac erased any other way gets no such stop.

**Suggested fix.** Before the "No changes" exit, compare HEAD with its upstream. When commits
are unpushed, or the branch has no upstream, push them and say so; when the push fails, exit
non-zero. A dry run reports the count and pushes nothing. The manual and SMAC-1 then say which
two last lines mean the remote is current.

**Fixed 2026-10-01, branch `claude/fix-x1-x3-reports`.**

**Fix.** `unpushed_count` (`scripts/snapshot-prefs:112`) counts the commits the branch holds
that its upstream lacks, as of the last push. It asks no network. At the "nothing staged" exit:
- **None unpushed:** "No changes to push.", exit 0, as before. That line now means mrk-prefs has
  the last commit.
- **Some unpushed:** "No changes to commit. Pushing N commit(s) that an earlier run left
  unpushed.", then `git push -u origin HEAD`, and the run ends on "Pushed to …". A push that
  fails exits with git's status.
- **A dry run:** it says how many commits the real run would push, and pushes nothing. The count
  is taken in the real `~/.mrk/preferences`, because the dry run's scratch clone has that
  directory as its upstream, and not mrk-prefs.
- **No upstream:** every commit counts. A first push that fails leaves a new repository in that
  state, on the `git init` path.

**What else it touches.**
- A `~/.mrk/preferences` left on a detached HEAD now ends in git's push error, where it ended
  in "No changes to push." before. The commit path already failed there.
- The comparison is with the last push, so a commit another Mac pushed since is not seen. The
  push is then refused as not fast-forward, with git's message, as on the commit path.
- A dry run that does find changes to commit still does not mention earlier unpushed commits.
  The real run's push carries them.

**Docs.**
- BIN-1's snapshot-prefs entry has a new item, and its `ci-check` entry describes the cases.
- `docs/manual.md`, "How to keep the app preferences current": the sentence about an earlier
  push. "How to prepare for a new machine", step 4: which two last lines are good, and that any
  other is a failure.
- sevmac, branch `claude/audit-20-reports`: SMAC-1 §2.4.1 and §2.6 step 4 say the same, and
  SMAC-2's card has one more sentence.
- `snapshot-prefs --help` says what "No changes to push." means.

**Test.** `tests/snapshot-prefs.sh`, cases 11 to 14, six checks:
- 11: a real change with the remote out of reach exits non-zero, keeps the commit, and does not
  say "Pushed to". A second run, the remote still out of reach and nothing new, exits non-zero
  too, and says neither "Pushed to" nor "No changes".
- 12: `-n` after it says the real run would push 1 commit, and writes and pushes nothing.
- 13: the real run pushes the commit, ends on "Pushed to", and the pushed value is this Mac's.
  The run after it says "No changes to push."
- 14: a second home whose `~/.mrk/preferences` is a plain directory, and a first push that
  fails. The next run pushes the commit, from a branch with no upstream.

## X-2 — One byte that is not UTF-8 makes the verdict say the run stopped short (MEDIUM, FIXED)

`scripts/lib.sh:616`:

```bash
found=$(sed -e $'s/\x1b\\[[0-9;?]*[A-Za-z]//g' -e $'s/\x1b][^\x07]*\x07//g' "$log" 2>/dev/null | tr -d '\r' | awk '
```

macOS's `sed` stops at the first byte sequence that is not valid in the locale: "RE error:
illegal byte sequence". The `2>/dev/null` hides the message. `awk` then sees only the lines
before that byte, finds no Summary, and `topgrade_verdict` takes its no-summary branch.

This Mac's shells run with `LANG=en_US.UTF-8`. Reproduced with a transcript in topgrade's own
form, one Latin-1 byte in a download line above the Summary, and `/usr/bin/sed`:

```
== LC_ALL=C
  ⚠ Update finished: every step ran. 1 of 2 failed: Brew Cask (ARM).
== LC_ALL=en_US.UTF-8
  ⚠ topgrade stopped before its summary (exit 1): not every step ran. Its last output is above.
```

**Why it matters.** "Not every step ran" is the one sentence the function's comment says must
never be wrong in the other direction, and #71 was a whole PR to stop this same false sentence
from another cause. The recording holds the output of every package manager topgrade runs. One
file name in another encoding, anywhere in a run, is enough. With exit 0 the no-summary branch
prints nothing, so the "all N steps succeeded" line is lost without a word.

**Suggested fix.** Run the three filters under `LC_ALL=C`. The patterns are byte strings, and
the same run above shows they match in the C locale. Keep the `2>/dev/null` only on the read of
the file.

**Fixed 2026-10-01, branch `claude/fix-x1-x3-reports`.**

**Fix.** The pipeline in `topgrade_verdict` (`scripts/lib.sh:624`) starts with
`export LC_ALL=C`, inside its command substitution, so the setting reaches `sed`, `tr` and `awk`
and nothing outside. The recording is read as bytes. The header patterns are byte strings, and
match as before.

All three filters need it, not `sed` alone. With `LC_ALL=C` on `sed` only, the same three checks
fail: macOS's `tr` and `awk` stop on the byte too.

**Test.** `tests/update-verdict.sh`, case 1c, three checks. Every case there ran in the C
locale, because `env -i` leaves no `LANG`, and that is why none saw this. The new ones run under
`LC_ALL=en_US.UTF-8`, with a Latin-1 byte in a line above the Summary:
- the plain and the wide form, one step failed: the Summary is read, and the verdict names the
  step
- nothing failed: it still says all 10 succeeded

Where `sed` reads such a byte without stopping, as GNU sed does, the cases run and cannot fail
for this reason. The test says so in a note, so that a pass there is not read as proof.

| Mutation | Failing checks |
|---|---|
| `scripts/lib.sh` as on `main` | 3 |
| the pipeline back in the caller's locale | 3 |
| the C locale kept for `tr` and `awk`, lost for `sed` | 3 |
| the C locale for `sed` alone | 3 |

BIN-1's `topgrade_verdict` row and its `ci-check` entry say what changed. SMAC-1 and SMAC-2
describe the verdict, not how it reads its recording, and need no change.

## X-3 — The dashboard calls a Safari update a major upgrade (MEDIUM, FIXED)

`tools/mrk-status/daily.go:556-566` sorts every entry of `RecommendedUpdates` by one test: the
major number of its `Display Version` against the installed macOS.

`bin/macos-updates:84-94` applies that test only to macOS itself, and says why:

> The version test that follows cannot be applied to everything: Safari and the Command Line
> Tools carry version numbers ahead of the OS — 27.0 for both on macOS 26 — and are not upgrades.

So the range holds two copies of the rule, and the newer one (#66) lacks the half the older one
was written around. A probe test on a scratch copy, with the fixtures `daily_test.go` uses
(macOS 26.0.1 installed; Safari 27.0 and Command Line Tools 27.0 on offer):

```
sev=OK   "No macOS update for macOS 26"
sev=info "  offered, and never installed by mrk, being a major upgrade: Safari, Command Line Tools for Xcode"
```

Both lines are false. `make updates` installs both updates, and the panel offers no
`make updates` fix because it counts nothing. `TestUpkeepMacOSUpdates` has only macOS entries, so
it passes.

BIN-1 (`docs/bin/mrk-usage.html:762`), the manual and SMAC-1 §2.8 all say the panel treats a
major upgrade "as macos-updates treats it". On this Mac today the only entry is macOS 27.0.1, so
the panel is right today.

**Suggested fix.** Apply the version test only to an entry whose name or identifier says macOS,
as `is_macos` does. Count every other entry as an update `make updates` installs. Add the Safari
and Command Line Tools case to the Go test.

**Fixed 2026-10-01, branch `claude/fix-x1-x3-reports`.**

**Fix.** `isMacOSUpdate` (`tools/mrk-status/daily.go:539`) is `is_macos` for an entry of
`RecommendedUpdates`: the update is macOS when its `Display Name`, `Identifier` or `Product Key`
says so, anywhere in it. An entry with no name is taken for macOS, as before. Only a macOS entry
takes the version test. Every other entry is counted as an update, with the `make updates` fix,
and shown with its version: "Safari 27.0".

The rule still lives in two places, bash and Go. The Go comment and the bash comment now give
the same reason, and the test below holds the Go side to it. One copy would mean the dashboard
running `softwareupdate --list`, which takes seconds and asks the network; the panel reads
macOS's own record so that it does neither.

**Test.** `TestUpkeepOnlyMacOSIsEverAMajorUpgrade`, on macOS 26.0.1:
- Safari 27.0, Command Line Tools 27.0 and macOS 27.0.1 on offer: two updates, both named with
  their versions and the `make updates` fix; one major upgrade, macOS 27.0.1. The macOS entry
  has the identifier this Mac's record held on 2026-10-01.
- Safari alone: one update, and no major-upgrade line.
- An entry whose identifier says macOS, and two with no name: each is judged by its version.

| no entry is macOS | the same, and `TestUpkeepMacOSUpdates` |
| an entry with no name is not macOS | the same |
| the identifier is not read | the same |
| Safari shown without its version | the same |

**On this Mac.** The built binary, run with `--plain` against the real record: "No macOS update
