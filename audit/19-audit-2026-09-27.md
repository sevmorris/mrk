## W-1 — A Mac without Homebrew cannot run Phase 1 or Phase 2 (CRITICAL, FIXED)

`scripts/setup:4-10` and `scripts/brew:4-10` carry the same guard:
1. under bash 3, re-exec with `/opt/homebrew/bin/bash` or `/usr/local/bin/bash`
2. with neither present, print "install via 'brew install bash'" and exit 1

It was added in `63a35a1` (2026-03-20) for a Mac that had Homebrew but had lost its PATH after
`nuke-mrk`.

**setup does not need it.** It uses no bash-4 syntax: no `declare -A`, no `-n`, no `${x,,}`, no
`mapfile`. With the guard deleted from a scratch copy, it ran four phases under macOS's
`/bin/bash` 3.2.57 in a throwaway HOME:
- `setup --only tools --dry-run`
- `--only dotfiles --dry-run`
- `--only shell --dry-run`
- `--only defaults --dry-run`

xcode was left out; see W-7.

**brew does need it.** It uses `declare -A`, `declare -n` and `${type_label,,}`. It is also the
phase that installs Homebrew, so on a new Mac it can never reach that step.

Reproduced on a scratch copy with the two Homebrew bash paths renamed, and `PATH=/usr/bin:/bin`:

```
== make setup (bash 3.2, no Homebrew bash)
error: bash 4+ required (system bash is 3.2.57(1)-release; install via 'brew install bash')
make: *** [setup] Error 1
== make brew (bash 3.2, no Homebrew bash)
error: bash 4+ required (system bash is 3.2.57(1)-release; install via 'brew install bash')
make: *** [brew] Error 1
```

**Where the broken path is prescribed:**
- README Quick Start: "For my machine, on a clean install: … `make -C ~/mrk all`"
- manual, How to set up a new machine, Steps 2 and 4
- BIN-1 2.11–2.13
- SMAC-1 §2.2 (sevmac): "`make brew` Installs Homebrew …"

None mentions installing Homebrew or bash first.

**Why nothing caught it.**

| Path | Has Homebrew's bash because |
|---|---|
| A test install | `nuke-mrk` does not uninstall Homebrew |
| CI | the workflow runs `brew install shellcheck bash gnupg` before `ci-check` |
| `tests/install-all.sh` | it stubs `make`, so no phase runs |
| The 2026-09-15 migration | the new Mac was set up with Homebrew already present |

The last row is inferred: the log of that day's first Phase 1 did not survive the 2026-09-24
reinstall (W-8).

**Fixed 2026-09-27, branch `claude/fix-w1-bootstrap-bash`.**

**Fix.** Neither script re-executes any more, and both run under `/bin/bash` 3.2.57:
- **setup** needed no bash 4, and only lost the guard.
- **brew** is now bash-3.2-clean:
  - newline-terminated lists, tested by `in_list`, replace its seven associative arrays
  - two indexed lists replace the description map
  - a `SELECTION` global replaces the two namerefs
  - the plural is spelled out rather than lowercased with `${x,,}`

  It takes `MRK_BREW`, as `sync` does, so a test can run it on a Mac with Homebrew as though it
  had none.

**Why this way, and not install-then-re-exec.** The other way kept brew's guard. Under 3.2 it
would first install Homebrew and Homebrew's bash, then re-execute. It was set aside for three
reasons:
- **Duplication.** It needs a second, 3.2-clean copy of the option parsing, the network check
  and the Homebrew install, ahead of the guard. That is two paths through Phase 2, and the one a
  new Mac takes would run only on a new Mac.
- **The dry run.** A dry run on a new Mac could not get past the guard without installing bash.
  It would stop at "would install Homebrew and bash".
- **Precedent.** One script that runs under either bash is how `lib.sh`, `macos-updates`,
  `install` and `post-install` already are, and `tests/new-mac.sh` runs it under both.

The cost is a rewrite of the package-selection code every Mac runs. That is checked below: main's
brew passes the same test under bash 5. The one visible change is the order of the chosen lines
handed to `brew bundle`. They now arrive in Brewfile order; before, they arrived in the order bash
hashed the names.

**Three more defects on the same path, found by the test.**
- **The dry run stopped past the guard.** On a Mac without Homebrew, `brew --dry-run` said it
  would install Homebrew, then looked for it and stopped with "Homebrew is not available", exit 1.
  So the reproduction above, `make brew ARGS=--dry-run`, would still have exited 2 with the guard
  gone. A dry run now skips that lookup when it has only said it would install Homebrew.
- **Under bash 3.2 an abort reported success.** When `set -u` aborts a script that has an EXIT
  trap, bash 3.2 runs the trap with `$?` at 0, and the script exits 0. Bash 5.3 exits 1.

  ```
  $ /bin/bash -c 'set -u; trap "echo trap" EXIT; echo "$x"'; echo $?
  /bin/bash: x: unbound variable
  trap
  0
  ```

  setup and brew both have EXIT traps. Once they run under 3.2, an unbound variable in either
  would have exited 0, and `make all` would have gone on to the next phase. Both traps now exit 1
  when the run did not reach its end. setup already marked that point with `MRK_SUCCESS`; brew
  gains `BREW_FINISHED`. brew's INT and TERM traps are as they were.
- **An empty array is unbound under bash 3.2.** setup's `for f in "${bin_files[@]}"` aborted
  when `bin/` held nothing executable. It now expands `${a[@]+"${a[@]}"}`. brew had one such
  loop, over both package arrays, and `--no-formulae` empties one of them. It is replaced by a
  flag set during the Brewfile scan.

## W-2 — Six apps' saved preferences are never imported on a new Mac (HIGH, FIXED)

`import_plist` (`scripts/post-install:622`) imports only into an empty domain. It tests that with
`defaults read "$bundle_id"`, which exits 0 as soon as the domain holds any key. Earlier in the
same run, two scripts write keys into six of the domains it later imports:

| Writer | Where | Domains it creates | Import it defeats |
|---|---|---|---|
| `rogue-amoeba-updates.sh`, unconditional | `post-install:523` | Audio Hijack, Fission, Loopback, Piezo, SoundSource, Farrago | `:676-680`: Loopback, SoundSource, Audio Hijack, Farrago, Piezo |
| `audio-hijack-defaults.sh` | `:510` | Audio Hijack | `:678` |
| `helium-defaults.sh` | `:321` | Helium | `:684` |

Each logs "exists — skipping import (won't overwrite)". The gate, shown on a scratch plist:
two `defaults write … SU… -bool false`, then `defaults read` → exit 0.

**This Mac bears it out.** The rollback lines in `~/.mrk/defaults-rollback.sh` are written only
when an import happens. The migration-day run left import lines for Ice, iTerm2, Raycast, Stats,
Typora, Keka, Waves Central, TimeMachineEditor, MacWhisper and the owner's apps. BetterSnapTool
and Picard were imported later. It left none for Loopback, SoundSource, Audio Hijack, Farrago,

| Plist | Added to mrk-prefs |
|---|---|
| Loopback, SoundSource, AudioHijack, Farrago, Piezo | 2026-03-01 |
| Helium | 2026-09-02 |
| Raycast, Stats, iTerm2 (imported, for comparison) | 2026-03-01 |

The Application Support files for Loopback and SoundSource are restored separately, by file, and
are not affected.

**Fixed 2026-09-27, branch `claude/fix-w2-plist-import-order`.**

**Fix.** The plist-import section of `post-install` moved, as one block, to before the browser
section, the first step that writes app defaults. The block holds the SSH check, the mrk-prefs
pull, `import_own_apps` and the 17 `import_plist` calls. Everything above it links files or adds
a JSON hook, and writes no preference domain. The app-defaults scripts now write mrk's keys over
the restored settings. `rogue-amoeba-updates.sh` also writes only to the Rogue Amoeba apps that
are installed, as every other app-defaults script already did. Moving the imports alone would
have left a second path: an app not installed on the first run still got the two Sparkle keys,
and the gate refused its import on every run after it was installed.

**Why the order, and not a gate that ignores mrk's own keys:**
- That gate needs a list of every key each script writes, kept in step by hand. A key added to a
  script and not to the list brings W-2 back without a word.
- With the scripts first, `backup_plist` finds a domain holding only mrk's keys and exports it.
  The rollback line then becomes `defaults import <domain> <backup>`, which records mrk's own
  keys as the original.
- That line would not undo the import either. On a scratch plist, `defaults import` merged: a key
  written before the import was still there after it. So restoring the backup leaves every
  imported key in place.

With the imports first, the domain is absent when `backup_plist` runs, so the rollback line is
`defaults delete <domain>`, as it is for the other eleven. The domain did not exist before mrk.

**What else the order touches:**
- **Rollback.** Each of the six imports now writes a `defaults delete` line. The scripts' keys,
  written after it, still get no line of their own (W-12), and the delete removes them with the
  domain. That adds six whole-domain deletes to what W-13 describes.
- **Application Support.** `restore_app_support` restores Loopback's and SoundSource's files one
  by one and skips any that exist. No defaults script writes there, and the step did not move.
- **The guarantees.** The gate is unchanged: it still asks `defaults`, so it still sees a
  sandboxed app's container. An app that is not installed is still skipped. `import_own_apps`
  still imports whether or not the app is installed. It now runs before `install_companion_apps`
  installs the apps, which is the order its comment asks for.
- Only the three scripts write into imported domains. A grep of `defaults.sh`, `setup`,
  `hardening.sh`, `dock-setup`, `trim-services` and `install-apps` for all 17 bundle ids, and
  `io.github.sevmorris.`, found no other writer.

**Test.** `tests/plist-import-order.sh`, run by `ci-check`. It runs `post-install` whole, from a

## W-31 — After Phase 2, `make all` does not see Homebrew (HIGH, found fixing W-1)

Added 2026-09-27 by the W-1 fix session. W-1 stopped a new Mac at Phase 1, which hid this. The
severity is a proposal, for the owner to confirm.

`make all` runs every phase with the PATH it was started with. On a new Mac that PATH has no
`/opt/homebrew/bin`, because the shell started before Homebrew existed. The manual's walkthrough
is in the same place: Step 2's `exec zsh` also comes before Phase 2. brew puts Homebrew on its own PATH with `brew shellenv` (`resolve_homebrew`), which reaches only
brew's process. What runs after brew finds nothing Phase 2 installed:
- **post-install** looks for three tools on PATH, and on a new Mac finds none:
  - topgrade (`:153`): "topgrade config (topgrade not installed)"
  - pyenv (`:621`): "pyenv bootstrap (pyenv not installed or no .python-version)", so no Python
  - pinentry-mac (`:811`): "gpg pinentry (pinentry-mac not installed)"

  Each is logged as a skip, and the run succeeds.
- **build-tools** checks `command -v go` and fails.

Shown read-only on a scratch copy, with this Mac's Homebrew in place and a new Mac's PATH:

```
$ env -i HOME=… PATH=/usr/bin:/bin:/usr/sbin:/sbin make -C <copy> build-tools
error: Go is not installed. Install it with: brew install go
make: *** [build-tools] Error 2
```

`/opt/homebrew/bin` holds `go`, `topgrade`, `pyenv` and `pinentry-mac`. None is found on that
PATH.

**What it breaks:**
- **The README quick start.** `make -C ~/mrk all` runs all three phases, then exits 2.
- **The manual's walkthrough.** Step 5, `make post-install`, runs in the shell Step 2 started, and
  skips the same three steps.

A new terminal, or `exec zsh` after Phase 2, recovers both: `.zprofile` then finds brew and runs
`shellenv`.

**Not fixed here: the fix is a choice.** Three candidates:
1. post-install and the Makefile's go check run `brew shellenv` when brew is at a known prefix,
   as brew does.
2. The Makefile prepends `/opt/homebrew/bin` to PATH for its recipes. This also reorders PATH for
   every other target.
3. The manual and SMAC-1 add `exec zsh` after Phase 2. That fixes the walkthrough, but not
   `make all`.

Also, SMAC-1 §2.2 Step 1 says `make all` "also builds the TUI binaries". On a new Mac it does not,
until this is fixed.

## W-3 — Two copies of the rollback check that can empty an undo file (MEDIUM)

`scripts/lib.sh`. The old check overwrites the file when it does not match. The new one tests
line 1 for any shebang, and moves an unrecognised file aside. `defaults.sh`, `post-install` and
`dock-setup` use it. Two writers kept the old check:
- `scripts/hardening.sh:49-57`: the undo file for the PAM edit, the firewall and Mac Analytics
- `scripts/trim-services:55-57`: the undo file for the launchd disables

Lines 40–57 of `hardening.sh`, run against a scratch HOME:

| Undo file before | After |

## W-8 — `services-rollback.sh` is never offered, and nuke-mrk trashes it (MEDIUM)
