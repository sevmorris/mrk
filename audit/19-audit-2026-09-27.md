**Scope:** every module (setup, brew, post-install, defaults, hardening, the `bin/` and

**One premise was false:** there is no `tools/bf`. The four Go modules are `picker`, `mrk-status`,

**Headline: a bootstrap tool that cannot bootstrap.** On a Mac with no Homebrew, `make setup` and
`make brew` both exit 1 at a bash-4 guard. That is the README's quick start and the manual's

- test installs go through `nuke-mrk`, which keeps Homebrew
- CI runs `brew install bash` before `ci-check`
- `tests/install-all.sh` stubs `make`

**Second headline: order of operations, again.** post-install writes two Sparkle keys into six
apps' preference domains, then declines to import their saved plists because the domains are no
longer empty. The migration-day rollback file shows it happened on this Mac.

## W-1 — A Mac without Homebrew cannot run Phase 1 or Phase 2 (CRITICAL)

`scripts/setup:4-10` and `scripts/brew:4-10` carry the same guard:
1. under bash 3, re-exec with `/opt/homebrew/bin/bash` or `/usr/local/bin/bash`
2. with neither present, print "install via 'brew install bash'" and exit 1

It was added in `63a35a1` (2026-03-20) for a Mac that had Homebrew but had lost its PATH after
`nuke-mrk`.

**setup does not need it.** It uses no bash-4 syntax: no `declare -A`, no `-n`, no `${x,,}`, no
`mapfile`. With the guard deleted from a scratch copy, it ran four phases under macOS's
`/bin/bash` 3.2.57 in a throwaway HOME:
- `setup --only tools --dry-run`
- `--only dotfiles --dry-run`
- `--only shell --dry-run`
- `--only defaults --dry-run`

xcode was left out; see W-7.

**brew does need it.** It uses `declare -A`, `declare -n` and `${type_label,,}`. It is also the
phase that installs Homebrew, so on a new Mac it can never reach that step.

Reproduced on a scratch copy with the two Homebrew bash paths renamed, and `PATH=/usr/bin:/bin`:

```
== make setup (bash 3.2, no Homebrew bash)
error: bash 4+ required (system bash is 3.2.57(1)-release; install via 'brew install bash')
make: *** [setup] Error 1
== make brew (bash 3.2, no Homebrew bash)
error: bash 4+ required (system bash is 3.2.57(1)-release; install via 'brew install bash')
make: *** [brew] Error 1
```

**Where the broken path is prescribed:**
- README Quick Start: "For my machine, on a clean install: … `make -C ~/mrk all`"
- manual, How to set up a new machine, Steps 2 and 4
- BIN-1 2.11–2.13
- SMAC-1 §2.2 (sevmac): "`make brew` Installs Homebrew …"

None mentions installing Homebrew or bash first.

**Why nothing caught it.**

| Path | Has Homebrew's bash because |
|---|---|
| A test install | `nuke-mrk` does not uninstall Homebrew |
| CI | the workflow runs `brew install shellcheck bash gnupg` before `ci-check` |
| `tests/install-all.sh` | it stubs `make`, so no phase runs |
| The 2026-09-15 migration | the new Mac was set up with Homebrew already present |

The last row is inferred: the log of that day's first Phase 1 did not survive the 2026-09-24
reinstall (W-8).

## W-2 — Six apps' saved preferences are never imported on a new Mac (HIGH)

`import_plist` (`scripts/post-install:622`) imports only into an empty domain. It tests that with
`defaults read "$bundle_id"`, which exits 0 as soon as the domain holds any key. Earlier in the
same run, two scripts write keys into six of the domains it later imports:

| Writer | Where | Domains it creates | Import it defeats |
|---|---|---|---|
| `rogue-amoeba-updates.sh`, unconditional | `post-install:523` | Audio Hijack, Fission, Loopback, Piezo, SoundSource, Farrago | `:676-680`: Loopback, SoundSource, Audio Hijack, Farrago, Piezo |
| `audio-hijack-defaults.sh` | `:510` | Audio Hijack | `:678` |
| `helium-defaults.sh` | `:321` | Helium | `:684` |

Each logs "exists — skipping import (won't overwrite)". The gate, shown on a scratch plist:
two `defaults write … SU… -bool false`, then `defaults read` → exit 0.

**This Mac bears it out.** The rollback lines in `~/.mrk/defaults-rollback.sh` are written only
when an import happens. The migration-day run left import lines for Ice, iTerm2, Raycast, Stats,
Typora, Keka, Waves Central, TimeMachineEditor, MacWhisper and the owner's apps. BetterSnapTool
and Picard were imported later. It left none for Loopback, SoundSource, Audio Hijack, Farrago,
Piezo or Helium, although each plist was in mrk-prefs beforehand:

| Plist | Added to mrk-prefs |
|---|---|
| Loopback, SoundSource, AudioHijack, Farrago, Piezo | 2026-03-01 |
| Helium | 2026-09-02 |
| Raycast, Stats, iTerm2 (imported, for comparison) | 2026-03-01 |

The Application Support files for Loopback and SoundSource are restored separately, by file, and
are not affected.

## W-3 — Two copies of the rollback check that can empty an undo file (MEDIUM)

The work of 2026-09-10 (ledger: "The rollback init guard could empty the undo button") replaced the whole-file check `grep -q '^#!/usr/bin/env bash$'` with `init_rollback` in
`scripts/lib.sh`. The old check overwrites the file when it does not match. The new one tests
line 1 for any shebang, and moves an unrecognised file aside. `defaults.sh`, `post-install` and
`dock-setup` use it. Two writers kept the old check:
- `scripts/hardening.sh:49-57`: the undo file for the PAM edit, the firewall and Mac Analytics
- `scripts/trim-services:55-57`: the undo file for the launchd disables

Lines 40–57 of `hardening.sh`, run against a scratch HOME:

| Undo file before | After |
|---|---|
| `#!/bin/bash` + two undo lines | `#!/usr/bin/env bash`, nothing else |
| `#!/usr/bin/env bash ` (trailing space) + two undo lines | `#!/usr/bin/env bash`, nothing else |
| the same `#!/bin/bash` file through `init_rollback` | unchanged |

As in 2026-09-10's analysis, mrk itself has only ever written the one shebang, so this is a
fragility rather than an active loss. The ledger records the duplication as the cause last time.

## W-4 — setup links git-ignored files, and can displace `~/.claude` (MEDIUM)

`phase_dotfiles` (`scripts/setup:444-543`) links every file in `dotfiles/`, as the filesystem has
it, except `*.example`, `README*` and `*.md`. Whatever is present on disk is linked, git-ignored
or not, directories included. `.gitignore:37` lists `dotfiles/.claude/`, which has been there
since the first commit, so that directory has existed before. Claude Code creates it for a
session started in `dotfiles/`. Finder makes a `.DS_Store` in a folder it opens.

Reproduced on a scratch copy with a throwaway HOME:
- setup: `dotfiles/.claude/settings.local.json` and `dotfiles/.DS_Store` present
- HOME: a real `~/.claude/` holding `settings.json` and `projects/`

`setup --only dotfiles`:

```
[2/10] Processing .claude...  ▸ Backing up: …/home/.claude -> …/home/.mrk/backups/20260927-163654/.claude
▸ Linked 10 dotfile(s)
```

`~/.claude` is now a link into the repository, and Claude Code's settings, sessions and memory
are in `~/.mrk/backups/`. They are moved, not deleted, but nothing restores them (manual, "What the
backups are"). `~/.DS_Store` became a link too. `mrk-status` and `status` count both as managed
dotfiles, because they use the same rule.

## W-6 — brew ignores `--no-casks`, `--no-formulae`, `--only-formulae` without a TTY (MEDIUM)

With `--yes`, or with no TTY on stdin, `install_brewfile` (`scripts/brew:413-423`) takes a
non-interactive branch. It runs `brew bundle --file="$BREWFILE" --no-upgrade`, which is the whole
Brewfile. The three flags are applied only in the interactive branch below it. The `mas`-line
guard at `:512` is bypassed the same way.

Reproduced, with a stub `brew` recording what it was given:

```
$ brew --yes --no-casks
brew bundle --file=…/Brewfile --no-upgrade --verbose
--- file …/Brewfile: casks=63 brews=53
```

This affects `make brew ARGS="--yes --no-casks"`, `mrk-install --brew --only-formulae` from a
script, and `make all ARGS=--yes` with either flag.

## W-8 — `services-rollback.sh` is never offered, and nuke-mrk trashes it (MEDIUM)

`trim-services` writes its undo to `~/.mrk/services-rollback.sh`. `nuke-mrk` protects undo files
this way (`bin/nuke-mrk:324-394`):
1. it offers to run `defaults-rollback.sh` and `hardening-rollback.sh`
2. when declined, it keeps those two and `plist-backups/`
3. it trashes the rest of `~/.mrk`

Its own comment gives the reason: "that is how this machine lost its hardening undo script". The
services undo is not among them, so it goes to the Trash while launchd keeps the disables, which
persist across restarts. `uninstall` never offers it either.

**It has happened once here, without harm.**
- Module 15 saw `~/.mrk/services-rollback.sh`, written 2026-09-15 12:46.
- `~/.mrk` was recreated at 2026-09-24 20:58:52, with `~/mrk` re-cloned seconds later.
- `defaults-rollback.sh` (born 2026-09-15), `hardening-rollback.sh` (2026-09-18) and
  `plist-backups/` (2026-09-15) came back with their birth dates.
- `services-rollback.sh` did not.
- No harm followed, because `launchctl print-disabled` lists none of the five services today
  (module 15's T-5: the disables had not held).
