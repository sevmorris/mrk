## P-1 — `restore-keys` rejects every valid archive (HIGH)

`scripts/restore-keys:92`

```bash
if ! gpg --list-packets --batch "$ARCHIVE" 2>&1 | grep -q "symkey enc packet"; then
  err "Not a snapshot-keys archive: $ARCHIVE"
```

`gpg --list-packets` prints the packet listing and *then* attempts the session key
anyway. With no passphrase available it exits 2 on `decryption failed: Bad session
key`. Under `set -o pipefail` that exit status becomes the pipeline's, even though
`grep` matched — so the guard fires on a perfectly good archive.

**Reproduced.** With `gpg 2.5.21` and no reachable agent, against an archive built
exactly as `snapshot-keys` builds one:

```
gpg --list-packets --batch <archive>   →  rc=2, prints ":symkey enc packet: version 4…"
without pipefail                       →  ACCEPTED
with    pipefail (as the script runs)  →  REJECTED
```

The script then tells the operator their only key backup is not a key backup. This runs
on a new machine, which is the sole situation `restore-keys` exists for.

A second defect sits in the same line. The comment on the sibling check in
`snapshot-keys` claims it "needs no passphrase". It does: without `--pinentry-mode
error` the agent raises a dialog here, before the real decrypt below.

**Fix.** Capture the output first so the packet listing decides rather than gpg's exit
status, and add `--pinentry-mode error` so no dialog is raised. Verified to accept a
valid archive and still reject a non-OpenPGP file.

## P-2 — `restore-keys` strands `~/.gnupg` (HIGH)

`scripts/restore-keys:118`

```bash
for d in .ssh .gnupg; do
  if [[ -e "$HOME/$d" ]]; then
    mv "$HOME/$d" "$backup"
```

Both directories are moved aside unconditionally. What the archive actually holds is
not knowable without decrypting it, so an archive made on a machine with no GPG — it
only contains `.ssh` — leaves the target machine with no live `~/.gnupg` at all. The
rollback trap only fires when the extract *fails*, so a successful restore is exactly
the case that loses the directory.

**Reproduced end-to-end.** Target with `.ssh` + `.gnupg`, archive with `.ssh` only:

```
BEFORE: .gnupg .ssh
AFTER : .gnupg.before-restore-<stamp> .ssh .ssh.before-restore-<stamp>
```

`~/.gnupg` survives only as a timestamped copy, which is not where gpg looks.

**Fix.** After a successful extract, put back anything the extract did not recreate,
and drop its copy — it is the live directory again, not a spare. Only a directory the
archive genuinely replaced is reported as a kept backup. Verified: `.gnupg` retains its
original contents while `.ssh` is correctly replaced from the archive.

## P-3 — `mrk-push` deletes the live Pages deployment (HIGH)

`bin/mrk-push:106`

```bash
to_delete=("${ids[@]:1}")
```

Everything except `ids[0]` is deleted. `bin/prune-deployments` already documents why
that rule is wrong, in its own header:

> "Keep the newest N" is not sufficient on its own. When a deploy fails, the newest
> deployment is the broken one and an older deployment is still serving the site.

The protection was written into the new standalone command and never back-ported to the
two places that actually run it. `mrk-push` is the worse of the two, because it prunes
*immediately after* `git push` — the moment when `ids[0]` is the newly queued
deployment and the older, successful one is what is serving the site. That older one is
then marked inactive and deleted.

This repository has already established that the consequence is real: N-16 rejected
`--keep=0` because it "selected the live deployment and took the published page
offline".

**Fix.** `mrk-push` now delegates to `bin/prune-deployments --repo <repo> --keep 1`,
which removes a duplicate implementation as well as the defect. Verified against the
live repo: `prune-deployments` identifies `#6160302109` as live and would delete only
the inactive `#6160148037`.

## P-4 — `snapshot-keys` carries the same check, masked (MEDIUM)

`scripts/snapshot-keys:292` — identical construction to P-1. It passes in practice for
an incidental reason: the passphrase was entered seconds earlier, so gpg-agent still
has it cached and the decrypt inside `--list-packets` succeeds.

**Demonstrated both ways** with a stub pinentry:

| agent cache | gpg rc | verdict |
|---|---|---|
| warm (immediately after encrypting) | 0 | passes |
| cold (a new machine) | 2 | rejects |

That asymmetry is why this survived four prior audits: the write side is always warm
and the read side is always cold. On any machine where the cache is cold or
`--no-symkey-cache` is set, `snapshot-keys` would discard a good archive after the
operator had already typed the passphrase, reporting "no archive written".

**Fix.** The same decoupling as P-1.

## P-5 — `maintain` shares the unprotected rule (MEDIUM)

`bin/maintain:116` — `to_prune=("${ids[@]:KEEP}")`, with no live-deployment check. Lower
risk than P-3 because `KEEP` defaults to 10, but the same flaw. Its header even records
the inheritance: "the deployment-pruning pattern from `bin/mrk-push`".

**Fix.** Live-deployment protection added inline rather than by delegation, because
`maintain` has an interactive confirmation and per-deployment progress output that
`prune-deployments` does not.

## P-6 — A changed LaunchAgent plist never takes effect (MEDIUM)

`scripts/post-install:742`

```bash
cp "$src_plist" "$dest_plist"
launchctl load "$dest_plist" >/dev/null 2>&1 || true
```

launchd keys a job by its `Label`, not by the file. `launchctl load` on a label that is
already loaded fails and leaves the previous definition running. The `cmp -s` guard
above returns early when the file is unchanged, so the only time this line is reached is
when the plist *changed* — precisely the case the bare load cannot apply.

**Reproduced** with a throwaway label, editing the scheduled hour from 3 to 9:

```
cp new plist; launchctl load   →  "Load failed: 5: Input/output error";  live Hour = 3
launchctl unload; launchctl load →  live Hour = 9
```

An edited schedule silently kept the old one until the next logout.

**Fix.** Unload before loading. The unload is expected to fail on a first install, hence
`|| true`.

## P-7 — LaunchAgents survive uninstall (MEDIUM)

Neither `bin/nuke-mrk` nor `scripts/uninstall` unloaded or removed
`com.user.clear_app_caches` or `com.user.clear_derived_data`. Both scripts *do* delete
the `~/bin` symlinks the agents invoke, so the result is a pair of registered jobs
firing on schedule against paths that no longer exist.

**Fix.** Both scripts now unload and delete the agents; unloading matters as much as
deleting, because launchd keeps a job registered regardless of the file. `nuke-mrk`'s
banner names them among what it removes.

## P-8 — bash-4 syntax with no re-exec guard (MEDIUM)

Ten scripts carry the `BASH_VERSINFO[0] < 4` re-exec guard. Three files use bash-4
syntax without it:

| File | Construct | Line |
|---|---|---|
| `bin/mrk-push` | `mapfile` | `:67`, `:91` |
| `scripts/snapshot-prefs` | `mapfile` | `:356` |
| `scripts/lib.sh` | `${_ans,,}` | `:47`, `:217` |

**Why no tool caught it.** These fail at *runtime*, not parse time:

```
/bin/bash -c 'v=ABC; echo start; echo "${v,,}"'
start
/bin/bash: ${v,,}: bad substitution
```

`bash -n` passes and shellcheck is silent, because both check syntax rather than the
running interpreter's version.

**Fix.** `mrk-push` and `snapshot-prefs` gain the standard guard. `lib.sh` is treated
differently: it is a shared library sourced by nine scripts that carry no guard, so
imposing a bash version on all of them is the wrong direction. It now lowercases with
`tr`, and sources cleanly under bash 3.2.

## P-10 — Cache scripts run unattended with no guards (LOW)

`bin/clear-app-caches` and `bin/clear-derived-data` are the only scripts in the tree
with no `set` line at all, and they are the only two that run unattended from a
LaunchAgent. An unset or empty `HOME` would turn every path into an absolute one
outside the home directory.

**Fix.** `set -uo pipefail` plus an explicit `HOME` check. `-e` is deliberately omitted
and the omission is documented: these are best-effort removals, and one cache that will
not delete should not stop the rest. Verified that an unset `HOME` now refuses with
status 1 while a normal run is unchanged.

## P-13 — `mrk-menu` offers a command that cannot succeed (LOW)

`tools/mrk-menu/data.go:54` listed `restore-keys` with no arguments. `restore-keys`
requires an archive path, and `update.go` runs a command through `exec.Command` with a
fixed argument list and no prompt, so the entry could only ever print the usage text and
exit 1.

**Fix.** Entry removed, with a comment recording why so it is not re-added. The manual
and BIN-1 both document `make restore-keys ARGS=<archive>`.

## P-14 — `scripts/lib.sh` is executable (INFO)

`scripts/lib.sh` was tracked `100755` while its own header reads "Source this file; do
not execute directly." `bin/lib/common.sh`, the sibling library, is correctly `100644`.
`scripts/fix-exec` was the cause: its `find … -maxdepth 1` reached into `scripts/` and
chmod-ed everything, while `bin/lib/` fell outside the scan.

**Fix.** `fix-exec` excludes `lib.sh`, and the file is tracked `100644`. Verified by
re-running `fix-exec` and confirming the bit is not re-added.

## What the tooling missed, and why

Worth recording, because it is the reusable part of this pass.

| Check | Result | Blind spot |
|---|---|---|
| `shellcheck -x` (35 scripts) | clean | Cannot see that a pipeline's exit status is semantically wrong (P-1, P-4) |
| `bash -n` under bash 3.2 | clean | `${x,,}` and `mapfile` fail at runtime, not parse time (P-8) |
| `go vet -all`, `gofmt -l` | clean | A menu entry that always exits 1 is valid Go (P-13) |
| `check-picker-desc` | 130 packages in sync | Scoped to the picker; no equivalent gate exists for BIN-1 (P-12) |
| `make check` | passed | Nothing exercises `restore-keys`, LaunchAgents, or deployment pruning |

**One bug class produced three findings.** P-1, P-4 and the pattern behind them are all
*validation coupled to an incidental exit status* — `if ! cmd | grep …` under
`pipefail`, where the interesting information is on stdout but the exit status comes
from a producer that failed for an unrelated reason. A sweep for that shape across the
tree found only these two sites; the others (`bin/pushall:90`,
`scripts/post-install:301,694`) are benign, because there the producer's failure and the
intended verdict agree.

**A second theme is duplicated logic drifting apart.** Deployment pruning existed in
three copies (P-3, P-5), and only the newest had the correction. The fix reduces it to
two, one of which is a delegation.

## Not changed

- The ~40 browser and app-preference writes with no rollback remain open. Unchanged
  since module 12; still the largest deferred item. See `00-followups.md`.
- `ARGS` word-splitting for value-bearing flags remains open and documented at
  `Makefile:140-141`.
- `bin/clear-app-caches` deletes caches of applications that may be running, and its
  LaunchAgent sets `RunAtLoad`, so it also runs at login. That is a design choice rather
  than a defect, and it was left alone — but it is worth a deliberate decision, since
  deleting a cache under a running Electron app is not always harmless.
