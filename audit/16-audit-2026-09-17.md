# Module 16 — The migration, checked end to end (2026-09-17)

**Date:** 2026-09-17
**Machine:** MacBook Pro 16-inch, Apple M5 Pro (`Mac17,8`), macOS 26.7 (`25G229`), two days
after the migration from the M3 on macOS 15.
**Scope:** is the migration complete and in good shape, with mrk, the tool that carried
it, as the focus? Module 15 audited mrk as it runs on this Mac. This module audits the Mac,
then follows each gap back into mrk.
**Baseline:** `52458c8` (PR #10). Module 15's open items were re-checked against the Mac, not
re-audited.
**Method:** mrk's read-only paths first (`make status`, `doctor`, `sync -n`,
`restore-repos -n`, `trim-services -n`, `setup --dry-run --only tools`, `ci-check`). Then the
machine itself: both GnuPG installations and the key restore's traces in `~/.gnupg*`, nvm,
the architecture of every app bundle, the login items' processes and crash reports, the
LaunchAgent and LaunchDaemon targets, Time Machine and Bonjour, the security settings,
Homebrew. Nothing that raises a permission prompt was run.

**Headline: the key restore split this Mac's GPG keyring in two.** `restore-keys` moved
`~/.gnupg` aside and then ran gpg to decrypt the archive. Homebrew's gpg 2.5.22 found no home
directory and made one. GnuPG 2.4.1 and later write `use-keyboxd` into the `common.conf` of a
home directory they make. tar then extracted the archive around that file. From then on
Homebrew's gpg, which KeyVault prefers, read its public keys from a keyboxd database, while
GPG Suite's gpg 2.2.41, which has no keyboxd, read the restored `pubring.kbx`. Nothing
reported it. The two keyrings had drifted by 2026-09-17: four keys in one, three in the other.

**Second headline: nvm is not Node.** Phase 3 installs nvm and stops, and nvm had no Node
version. The old Mac's Node had been installed by hand years ago, so the gap never showed.
This Mac has had no `node` or `npm` since the migration.

## U-1 — `restore-keys` let GnuPG switch the restored `~/.gnupg` to keyboxd (HIGH, FIXED)

**The timeline, from the files themselves.**

| Time (2026-09-15) | Event | Evidence |
|---|---|---|
| 12:19:12–14 | GPG Suite's installer creates `~/.gnupg`, with a `pubring.kbx` | the moved-aside copy's mtimes |
| 12:35:32 | Phase 3 writes `pinentry-program` into `gpg-agent.conf` | same |
| 12:37:39 | `restore-keys` moves `~/.gnupg` aside | `~/.gnupg.before-restore-20260915-123739` |
| 12:37:39 | `common.conf` = `use-keyboxd` appears in the new `~/.gnupg` | its mtime; every archived file keeps its old-Mac mtime |
| 18:10 | Keys are imported into keyboxd: `public-keys.d/pubring.db` and `trustdb.gpg` both change | mtimes |
| 2026-09-16 11:10:59 | `pubring.kbx` is rewritten, three keys before and after | `pubring.kbx~` |

`common.conf` is not from the archive. tar sets each extracted file's mtime from the archive,
and this one carries the second of the restore. gpg made it while decrypting. The 18:10
import is consistent with someone finding `gpg --list-secret-keys` empty after the restore and
importing the keys into keyboxd by hand. The symptom was treated, and the cause stayed.

**The state on 2026-09-17.** Homebrew's gpg listed four public keys and GPG Suite's three. The
three shared keys exported byte-identical from both stores. The fourth,
`0FF11AF081E98345594812037091115F8320B897` (Francois Dupoux), existed only in keyboxd. It was
never in `pubring.kbx`: not in the live file, and not in the pre-rewrite `pubring.kbx~` either.
`gpg.conf` sets `auto-key-retrieve`, so a signature check probably fetched it. KeyVault's
`GPGLocator` tries `/opt/homebrew/bin/gpg` first, so KeyVault and GPG Keychain listed different
keys.

**Fix, tool.** `scripts/restore-keys` makes a scratch home directory with `mrk_mktemp_d`. It
runs every gpg call there: the archive check, `-l`, and the decrypt. It kills that
directory's agent and deletes it on every exit path. `~/.gnupg` now holds exactly what the
archive holds. A side benefit: the archive check no longer creates a `~/.gnupg` on a Mac that
has none, which the restore then moved aside as a stray `.before-restore` copy.

One trap found on the way. The failure-path trap ran `restore_originals` and then the scratch
cleanup. `restore_originals` returns the failure status, and under `set -e` that ends the
trap, so after a wrong passphrase the scratch directory stayed behind. The trap is now
`restore_originals || true; cleanup_gpg_scratch`. The script's exit status is unchanged, because
a trap that finishes normally does not alter it.

**Test.** `tests/restore-keys.sh`, run by `ci-check`. A real gpg builds a `pubring.kbx`
keyring and an archive in the same shape `snapshot-keys` writes. A gpg stub first on PATH
supplies the passphrase. The test restores into throwaway homes in `$TMPDIR`, which are kept
short because gpg-agent's socket path is limited to 104 bytes. It runs 14 checks under
`/bin/bash` 3.2.57 and 14 under Homebrew bash 5.3.20:

- a home with a `~/.gnupg` already there
- a home with none
- a wrong passphrase: the originals come back, and the scratch directory is removed
- `-l`: it lists the archive, writes nothing, and leaves nothing behind

The passphrase is generated per run, so the tracked-file secret scan has no literal to flag.
The CI workflow now installs `gnupg`.

**Mutation check.** Three broken variants, each run against a scratch copy of the repo. The
test catches every one:

| Variant | Failing checks |
|---|---|
| `restore-keys` at `main` | 12 |
| decrypt without `--homedir` (the archive check still scratch) | 8 |
| trap without `\|\| true` | 2 |

**Fix, state.** On this Mac:

- `~/.gnupg/common.conf` was renamed `common.conf.use-keyboxd-retired-20260917`
- `keyboxd` was stopped
- the keyboxd-only public key was exported and imported into `pubring.kbx`
- `public-keys.d/` was left in place, unused

Both installations now list the same four public and three secret keys, and `gpg --export`
of the whole keyring is byte-identical from both.

## U-2 — Phase 3 installed nvm but never a Node version (MEDIUM, FIXED)

`nvm ls` printed `N/A` for everything, and the default alias resolved to `node → stable → N/A`.
`doublender-dashboard` (`npm ci`, wrangler 4, vitest 3.2) and `hacks-checklist` cannot run.

**Fix.** A step after nvm in `scripts/post-install`. When nvm has no default version, it runs
`nvm install -b --lts` and `nvm alias default <major>`:

- **`-b`** installs a prebuilt binary or nothing. A source build would meet the
  Xcode-newer-than-macOS trap that the pyenv section documents.
- **The alias is the major, such as `v24`.** nvm re-points `lts/*` whenever a newer LTS line
  appears. A `lts/*` default then names a version that is not installed, and every new
  shell has no node.
- **An existing default is left alone.** Moving to a new major is a decision, not a bootstrap
  step.

nvm.sh does not tolerate `set -eu`, so each use runs in a subshell with both off.

**Verified** under `/bin/bash` 3.2 with `set -euo pipefail`, by extracting the block and
running it against a stub nvm that also trips on `set -u`. Four cases:

| Case | Result |
|---|---|
| no default | installs, aliases `v24`, `failed=0` |
| install fails | warns, `failed=1` |
| default present | skipped, no install call |
| no nvm | skipped |

**State, fixed with the owner's go-ahead.** The same two commands ran here. nvm downloaded
`node-v24.21.0-darwin-arm64.tar.xz` from nodejs.org and matched its SHA-256. On this first
install, nvm then made a default of its own, `default -> lts/*`: the footgun described above,
which the step exists to avoid. `nvm alias default v24` replaced it. A clean login shell now
has node v24.21.0 (arm64) and npm 11.19.0.

## U-4 — Ice crashes at launch on macOS 26.7, and is still a login item (MEDIUM, FIXED)

Seven of the eight login items in `scripts/post-install` were running. Ice was not. There
are five crash reports from its launches:

- 2026-09-15 18:50
- 2026-09-16 07:40, twice, one minute after the 07:39 boot
- 2026-09-16 07:43, twice

All five are Ice 0.11.12 on macOS 26.7, with `EXC_BREAKPOINT` in a Swift concurrency task,
at the same offset. The app has been dead on this Mac since the migration. On the old Mac's
macOS 15 it worked.

0.11.12 (2024-10-29) is Ice's latest stable release. The Tahoe fixes are in a pre-release,
0.11.13-dev.2 (2025-09-16), which Homebrew carries as `jordanbaird-ice@beta`. Upstream still
has open Tahoe issues, among them #946 (2026-05-14, "Tahoe 26.5 update broke hidden
elements") and #823 (whether a stable Tahoe release is coming). Thaw
(`thaw-app/Thaw`, 2.0.1 on 2026-09-02, GPL-3.0, cask `thaw`) is a maintained menu bar manager
that requires macOS 26.

**Options:**

- Switch to `jordanbaird-ice@beta`. It keeps Ice's bundle ID and restored preferences.
- Move to Thaw.
- Drop the app, and use System Settings › Menu Bar.

**Decision: Thaw.** `brew install --cask thaw` installed 2.0.1: bundle ID `com.stonerl.Thaw`,
team `456BPWQ6U5`, accepted by Gatekeeper, universal. `brew uninstall --cask jordanbaird-ice`
removed Ice.app and its login item. It did not zap, so
`~/Library/Preferences/com.jordanbaird.Ice.plist` is kept.

In mrk, Thaw replaces Ice everywhere Ice was named:

- the Brewfile cask, in alphabetical place after `temurin@21`
- the picker description
- `add_login_item`, sorted as `sync-login-items` writes it
- the plist round trip in `snapshot-prefs`, `post-install` and `bin/snapshot`
- README's login-items row, the manual's list and table, the app lists in BIN-1's snapshot
  and snapshot-prefs entries, and SMAC-1's login-items sentence and both tables

`Ice.plist` stays in mrk-prefs, as Descript's did. `Thaw.plist` arrives with the first
`snapshot-prefs` after Thaw is set up; until then `post-install` logs a skip for it.

**Left to the owner:**

- Start Thaw, and give it the Accessibility access it asks for. A menu bar manager cannot
  work without it, and the grant is the owner's to make.
- Arrange the menu bar.
- Let Thaw start at login, with its own setting or with `make post-install`. That run asks
  once for Automation access to System Events.

## U-5 — No Time Machine destination (HIGH, your action)

`tmutil destinationinfo`: "No destinations configured". This Mac has had no backup since the
migration. Module 15 noted it under T-9, but as a reason to question `hide_tm.sh`. It is the
larger problem. A 5-second Bonjour browse shows `raspi` advertising `_adisk._tcp` (a Time

**To close:** add it in System Settings › General › Time Machine. That needs the share's
password, and a first backup.

## U-7 — GPG Suite's 2.2.41 agent serves Homebrew's gpg 2.5.22 (LOW, decision)

The running `gpg-agent` is MacGPG2's (`--use-standard-socket --daemon`). After U-1's fix,
Homebrew's gpg says so on writes: "server 'gpg-agent' is older than us (2.2.41 < 2.5.22)". Both
installations are in the Brewfile (`gnupg`, `gpg-suite-no-mail`), so the old Mac had the same
arrangement. This is not a migration regression.

Keeping both means the older agent serves the newer gpg, and a future keyboxd-only feature
reopens U-1's split. **To close:** keep one GnuPG. Drop `gpg-suite-no-mail` if GPG Keychain
and its Services menu are not used. Otherwise, accept the warning.

## U-8 — A required git-lfs filter with no git-lfs (LOW, decision)

`dotfiles/.gitconfig` has `[filter "lfs"] … required = true`. git-lfs is not installed and
not in the Brewfile, and no repository here uses LFS: no `filter=lfs` in any `.gitattributes`.
A clone of an LFS repository would fail with "git-lfs: command not found". **To close:** delete
the section, or add `brew "git-lfs"`.
