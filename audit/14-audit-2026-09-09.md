## P-1 — `((ERRORS++))` aborts the run it exists to keep alive (MEDIUM)

`scripts/setup:170`, `scripts/setup:434`, `scripts/setup:557`, `scripts/brew:657`.

`((x++))` is a post-increment: it evaluates to the value *before* the increment. When that
value is `0`, the arithmetic command's exit status is `1`. Under `set -e` that terminates
the shell. The increment still happens — only the status is non-zero — so the counter is
correct and the script is dead.

```bash
$ for v in 0 1 2; do echo "x=$v -> exit $( x=$v; ((x++)); echo $? )"; done
x=0 -> exit 1
x=1 -> exit 0
x=2 -> exit 0
```

It therefore fires only on the **first** increment of a counter that starts at zero, which
is why it has survived thirteen prior cycles.

`scripts/setup:167-171`:

```bash
if (( CONTINUE_ON_ERROR )); then
  if ! "$@"; then
    warn "Phase $name failed, continuing with remaining phases..."
    ((ERRORS++))      # ERRORS is 0 on the first failure → exit 1 → set -e → abort
    return 0
  fi
```

`ERRORS=0` at `scripts/setup:139`. `run_phase` is called plainly (`scripts/setup:651`,
`654`, `657`, `660`, `663`), so `set -e` is live inside it, and the body of
`if ! "$@"` is not a condition context. The first phase that fails under
`--continue-on-error` therefore aborts the script instead of continuing — precisely the
opposite of the flag's contract.

It is conditional, not deterministic: if the failing phase already incremented `ERRORS` on
its way out via `scripts/setup:434`, then `ERRORS` is `1` by the time line 170 runs, the
increment returns `0`, and the run continues. So the flag works or aborts depending on
*which* phase fails first and by which path. `scripts/brew:657` has the identical shape —
`main` is called plainly at `scripts/brew:698`, and `install_brewfile` may or may not have
incremented `ERRORS` before returning non-zero.

**Reproduction** — the same function, called two ways:

```bash
f(){ local c=0; ((c++)); echo "f finished c=$c"; }

f                 # plain call      → exit 1, "f finished" never prints
f || failed=1     # joined by ||    → completes, c=1
```

`scripts/setup:557` (`((WARNINGS++))` in `phase_defaults`) is reachable on the *default*
path rather than the `--continue-on-error` one: `run_phase`'s `else` branch invokes the
phase as a bare `"$@"` (`scripts/setup:174`), so `set -e` is live inside it, and
`WARNINGS` is `0` at `scripts/setup:140`.

**This hazard is already known in this file.** `scripts/setup:501`, `:507` and `:514` write
`((backed_up++)) || true` and `((linked++)) || true`. The guard is understood and applied
in the dotfile-linking path and omitted in the four sites above, so this is an
inconsistency rather than an unrecognised risk — which also makes it cheap to fix.

**Fix (applied):** the assignment form, which this repo already uses elsewhere —
`ERRORS=$(( ERRORS + 1 ))`, as in `scripts/defaults.sh` (`failed=$(( failed + 1 ))`).
`(( x++ )) || true` also works but reads as though the increment might fail.

All **twelve** matching sites were converted, not just the four that were live bugs. The
eight safe ones are safe only because of a call site in another function; changing
`if ! install_brewfile` to a plain call at some later date would silently convert four of
them into the same defect, with nothing to catch it. Converting the class rather than the
instances also stops the next sweep re-deriving the eight-safe / four-real analysis from
scratch.

Verified after the change:

```
--- OLD form: ((ERRORS++)) ---
  phase one failed, continuing...
  exit=1                                  # phase two never ran
--- NEW form: ERRORS=$(( ERRORS + 1 )) ---
  phase one failed, continuing...
  phase two failed, continuing...
  ALL PHASES ATTEMPTED, ERRORS=2
  exit=0
```

## P-2 — WITHDRAWN: the cache scripts are already guarded

**This finding was wrong.** All four scripts already carry an appropriate `set -` line:
`bin/clear-app-caches:7` and `bin/clear-derived-data:8` (`set -uo pipefail`),
`bin/clean-ds:25` and `bin/decloud:15` (`set -euo pipefail`). The precise hazard claimed —
an unset `HOME` turning every path absolute — is explicitly guarded:

```bash
if [[ -z "${HOME:-}" || ! -d "$HOME" ]]; then
  echo "error: HOME is unset or not a directory — refusing to remove anything" >&2
  exit 1
fi
```

The omission of `-e` is deliberate and commented in both files: *"these are best-effort
removals, and one cache that will not delete should not stop the rest from being cleared."*
This is Module 13's P-10, fixed at the time.

**How it failed:** detection used `head -5 | grep 'set -'`, and in these files the `set -`
line sits at 7, 8, 15 and 25 — outside the window. The check was then never re-run against
the whole file before the finding was written up.

That is the same error the headline of this document warns about, committed while writing
the document: a cheap pattern match was treated as evidence instead of as a pointer to
something that needs reading. It is recorded rather than deleted because a withdrawn
finding is the useful half of an audit trail — the next cycle can see that these four
scripts were examined and found correct, which is exactly what a deleted entry would not
say.

## P-3 — A failed firewall read is recorded as "was off" (LOW)

`scripts/hardening.sh:149-151`.

```bash
prev="off"
fw_state=$(/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate 2>/dev/null || true)
if grep -qi "enabled" <<< "$fw_state"; then prev="on"; fi
```

`|| true` converts a failed read into an empty string, and the initialiser leaves `prev` at
`"off"`. The rollback line written at `scripts/hardening.sh:167` is then
`--setglobalstate off`. If the firewall was actually **on** and the read merely failed,
running `~/.mrk/hardening-rollback.sh` would disable it.

The initialiser is what keeps the rollback line well-formed — without it an empty `prev`
would emit `--setglobalstate` with no argument — so this is a trade, not an oversight. But
it is the same class as the analytics-read bug fixed earlier (a failed read taken as a
known state), at a site that never received the same treatment. The three-way read used for
analytics is the pattern to copy: distinguish *read succeeded and says off* from *read
failed*, and skip writing a rollback line in the second case.

**Fix (applied):** the reads now use the `prev_absent` / `prev_stealth_absent` flags, the
same shape the screensaver keys forty lines above already use (`prev1_absent`,
`prev2_absent`). On a failed read the script warns and records **no** rollback line, while
still enabling the firewall — a firewall left on is not a harm, whereas a rollback line
inventing "it was off" is.

Verified against three stubbed `socketfilterfw` outcomes:

```
--- read fails ---   warn: … recording no rollback line      (was: --setglobalstate off)
--- reads enabled -- ROLLBACK LINE: … --setglobalstate on
--- reads disabled - ROLLBACK LINE: … --setglobalstate off
```

## P-4 — `mrk-status` reports every Brewfile package missing when `brew list` fails (MEDIUM)

`tools/mrk-status/main.go:339-368`.

```go
instF, instC := map[string]bool{}, map[string]bool{}
if out, err := exec.Command("brew", "list", "--formula").Output(); err == nil {
    for _, p := range strings.Fields(string(out)) { instF[p] = true }
}
```

On failure the `if` body is skipped and `instF` stays an **empty map**. The loop below then
tests `if instF[pkg]` for every Brewfile entry, every lookup returns false, and all **127**
packages render as `sevErr` — `pkg (missing)`. The dashboard shows 127 fabricated failures
and gives no indication that the check itself did not run.

The absent-brew case *is* handled: `tools/mrk-status/main.go:332` uses `exec.LookPath` and
reports `brew unavailable — skipping checks`. So the author considered brew missing but not
brew *present and failing* — a broken prefix, a partial upgrade, a permissions problem.

This is the recurring class this repo already names. `scripts/sync:190-194` carries the
guard for the identical call, with the reasoning in-line:

```bash
# Capture with an exit-code check (like brew leaves above): a failed list must
# not silently yield an empty set, which --prune would read as "every tracked
# entry is stale" and offer to delete the whole Brewfile.
if ! _formulae_out=$($HOMEBREW list --formula 2>/dev/null); then
  err "brew list --formula failed — cannot determine installed formulae"
  exit 1
fi
```

`sync` is destructive and so the consequence there was data loss; `mrk-status` is read-only
and the consequence is a false alarm. That difference is why the fix reached one and not the
other.

**Fix (applied):** the two calls are now made unconditionally and their errors checked. If
either fails, `checkBrewfile` returns a `sevWarn` group — the tracked counts plus
`cannot check what is installed — brew list --formula failed: …` — and never reaches the
per-package loop. `tools/mrk-status/main_test.go` covers both halves: a failing stub `brew`
must produce no "(missing)" rows, and a *succeeding* stub that lists nothing must still
report genuinely missing packages, so the fix does not trade one wrong answer for another.
Mutation-checked: against the pre-fix code the first test fails with
`0/2 installed, 2 missing`.

## P-5 — An EXIT trap ending on a false test fails a successful run (MEDIUM)

`scripts/brew:84`, `scripts/snapshot-keys:158`. Found by running the commands, not by
reading them.

```bash
cleanup() {
  [[ -n "$TEMP_BREWFILE" && -f "$TEMP_BREWFILE" ]] && rm -f "$TEMP_BREWFILE"
}
trap cleanup EXIT
```

A bare `[[ … ]] && cmd` returns 1 when the test is false, and as the last command of an
EXIT trap that status becomes the script's. On a dry run `TEMP_BREWFILE` is never created,
so the test is false and `brew --dry-run` exited **1** having done everything correctly and
printed *"Dry run complete. No changes were made."* `snapshot-keys -n` exited 1 the same
way — `SIGNING_STAGE` is empty on a dry run and with `--no-signing`.

Reduced to the mechanism:

```bash
STAGE=""; cleanup(){ [[ -n "$STAGE" ]] && rm -rf "$STAGE"; }; trap cleanup EXIT
echo "work done"        # → exit 1

STAGE="/tmp"            # same script, test now true
                        # → exit 0
```

**As with P-1, the guard is already in this repo.** `scripts/sync:80-82` ends every cleanup
line with `|| true`, and `scripts/sync-login-items:64` does the same inside its loop;
`scripts/setup:86` ends its cleanup with an `if` block, which returns 0. Three of five got
it right. The two that did not are the two that reported failure on success.

**Fix (applied):** `|| true` on both, matching `sync`'s existing style. Verified after:
`brew --dry-run` → 0, `snapshot-keys -n` → 0, `make brew ARGS=--dry-run` → 0.

## P-6 — `mrk-push` has no argument parsing (LOW)

`bin/mrk-push:46` is `msg="${1:-}"`, and there is no option handling anywhere in the file.
Every argument is taken as a commit message, so `mrk-push --help` **commits and pushes**
with `--help` as the message. That is not hypothetical: it happened during this
verification pass and required an amend and a force-push to repair.

Its sibling `bin/pushall` has both `--help` and `--dry-run`. Same shape as P-1 and P-5 — a
convention applied to one of a pair and not the other.

**Fix (applied):** `-h`/`--help` prints usage, anything else beginning with a dash is
refused rather than silently becoming a subject line, and `--` still lets a message begin
with a dash. Verified with the repo's HEAD and dirty-count captured either side: `--help`
exits 0 printing usage, `--bogus` and `-n` exit 1 refusing, and the repo is untouched by
all three. BIN-1 was updated in the same pass, since `CLAUDE.md` requires flags to be
documented there in the commit that adds them.

## P-7 — Two small inconsistencies between paired commands (INFO)

`bin/mrk-menu` is the only one of the three TUIs with no `--help`: `mrk-status` prints a
help page and `mrk-picker` gets one from Go's flag package, while `mrk-menu --help` tries
to open a TTY, fails, and exits 1. Separately, `scripts/brew` accepts `--dry-run` but not
`-n`, while `scripts/sync` accepts `--dry-run|-n`; the Makefile advertises `ARGS=-n` for

**Fix (applied):** `mrk-menu` gained a `usage()` in `mrk-status`'s shape, with its key list
taken from `viewHelp` so the two cannot drift, and `scripts/brew` gained `-n` as an alias
for `--dry-run`. Verified: all three TUIs answer `--help` with exit 0, and
`make brew ARGS=-n`, `make brew ARGS=--dry-run` and `./scripts/brew -n` all exit 0. BIN-1
gained both — and while documenting brew, its entry turned out to advertise
`mrk-brew [options]` while listing none, so all seven are now written down.

## P-8 — `make defaults` failed on the same key every run (LOW)

`scripts/defaults.sh:520`. Found by running `make defaults`, which had never been done
during an audit because it writes to the machine.

```
defaults[50862]: Could not write domain …/Containers/com.apple.mail/…/com.apple.mail; exiting
  ⚠ 1 default(s) failed to apply
```

Mail is sandboxed. Its preferences live under
`~/Library/Containers/com.apple.mail/Data/Library/Preferences`, and that domain does not
exist until Mail has been configured — the container directory alone is not enough, and it
*is* present here, which is what makes the failure look puzzling. `defaults write` into a
missing container domain does not create it; it fails outright. On a machine where Mail has
never been set up, every run of `make defaults` therefore ended with
`⚠ 1 default(s) failed to apply`.

The cost is not the unwritten preference, which is moot on a machine with no Mail account.
It is that a warning present on every single run is a warning nobody reads, and a real
failure would have hidden inside it.

There is a second-order effect worth recording: because `write_default` saves the rollback
line *before* attempting the write, and `defaults read` on the absent key fails, the
rollback carries `defaults delete com.apple.mail AddressesIncludeNameOnPasteboard` — an
entry for a change that never happened. It is inert (`|| true`), and it is the single
`delete` entry among the 125 in V-14.

**Fix (applied):** read the domain first and skip with a reason when it is absent. Reading
is the test that matters — `-d` on the container passes even when the plist has never been
written. Once Mail is configured the next run picks it up, so nothing is permanently
skipped. A run now ends:

```
  · Mail AddressesIncludeNameOnPasteboard (Mail has no preferences domain yet)
  ✓ Defaults applied.
```

`check-defaults-desc` still counts 143 keys — the gate's regex tolerates the leading
whitespace of the now-indented call, so the key stays documented.

## Verified clean

**V-1 — Rollback fidelity holds, in both rollback scripts.** `scripts/defaults.sh`
`write_default` records `defaults write <domain> <key> -<original-type> <original-value>`

## What the tooling missed, and why

`make check` is green at `c460f02`: `check-picker-desc` (127 packages), `check-defaults-desc`
(143 keys), `shellcheck`, and `go test` in all four modules.

Nothing here is reachable by that tooling. `shellcheck` does not model `set -e` propagation
through function call context — it cannot know that `((ERRORS++))` is fatal in `run_phase`
and harmless in `install_brewfile`, because the difference is at the *call site*, in a
different function, sometimes hundreds of lines away. P-2 is a missing line, which no linter
flags. P-3 requires knowing what `socketfilterfw` returns on failure and what the rollback
would then do — semantics no static tool has.

The generalisable lesson is V-6's: **for this bug class, the grep result is the beginning
of the analysis, not the end.** Any future sweep for `set -e` hazards must resolve the call
context of the enclosing function before reporting, or it will be wrong most of the time.
