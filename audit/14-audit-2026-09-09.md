# Module 14 — Full Sweep Audit (2026-09-09)

**Date:** 2026-09-09
**Scope:** every script under `scripts/` and `bin/`, the `dotfiles/`, and the Go source
under `tools/` (picker, mrk-status, mrk-menu, theme). Weight on five dimensions named in
the request: shell correctness under `set -e`/`set -u`; rollback fidelity; secret-scanner

**Method:** targeted greps to enumerate candidate sites, then a line-by-line read of each

**Headline: the call context is the whole audit.** Twelve sites matched the "unguarded
`((x++))` under `set -e`" pattern by grep. Eight are harmless because the enclosing function
is invoked in a condition (`if ! f`, `f || …`), which suppresses `set -e` through the entire
function body. Four are real because their enclosing function is invoked plainly. A
grep-driven audit would have reported all twelve and been wrong about eight — a 67%
false-positive rate on the single dimension most likely to be swept for, and the errors run
in both directions: `scripts/post-install:97` looks like the worst case in the repo and is
harmless, while `scripts/setup:557` looks incidental and fires on the default path.

re-investigated:

## P-1 — `((ERRORS++))` aborts the run it exists to keep alive (MEDIUM)

`scripts/setup:170`, `scripts/setup:434`, `scripts/setup:557`, `scripts/brew:657`.

`((x++))` is a post-increment: it evaluates to the value *before* the increment. When that
value is `0`, the arithmetic command's exit status is `1`. Under `set -e` that terminates
the shell. The increment still happens — only the status is non-zero — so the counter is
correct and the script is dead.

```bash
$ for v in 0 1 2; do echo "x=$v -> exit $( x=$v; ((x++)); echo $? )"; done
x=0 -> exit 1
x=1 -> exit 0
x=2 -> exit 0
```

It therefore fires only on the **first** increment of a counter that starts at zero, which
is why it has survived thirteen prior cycles.

`scripts/setup:167-171`:

```bash
if (( CONTINUE_ON_ERROR )); then
  if ! "$@"; then
    warn "Phase $name failed, continuing with remaining phases..."
    ((ERRORS++))      # ERRORS is 0 on the first failure → exit 1 → set -e → abort
    return 0
  fi
```

`ERRORS=0` at `scripts/setup:139`. `run_phase` is called plainly (`scripts/setup:651`,
`654`, `657`, `660`, `663`), so `set -e` is live inside it, and the body of
`if ! "$@"` is not a condition context. The first phase that fails under
`--continue-on-error` therefore aborts the script instead of continuing — precisely the
opposite of the flag's contract.

It is conditional, not deterministic: if the failing phase already incremented `ERRORS` on
its way out via `scripts/setup:434`, then `ERRORS` is `1` by the time line 170 runs, the
increment returns `0`, and the run continues. So the flag works or aborts depending on
*which* phase fails first and by which path. `scripts/brew:657` has the identical shape —
`main` is called plainly at `scripts/brew:698`, and `install_brewfile` may or may not have
incremented `ERRORS` before returning non-zero.

**Reproduction** — the same function, called two ways:

```bash
f(){ local c=0; ((c++)); echo "f finished c=$c"; }

f                 # plain call      → exit 1, "f finished" never prints
f || failed=1     # joined by ||    → completes, c=1
```

`scripts/setup:557` (`((WARNINGS++))` in `phase_defaults`) is reachable on the *default*
path rather than the `--continue-on-error` one: `run_phase`'s `else` branch invokes the
phase as a bare `"$@"` (`scripts/setup:174`), so `set -e` is live inside it, and
`WARNINGS` is `0` at `scripts/setup:140`.

**This hazard is already known in this file.** `scripts/setup:501`, `:507` and `:514` write
`((backed_up++)) || true` and `((linked++)) || true`. The guard is understood and applied
in the dotfile-linking path and omitted in the four sites above, so this is an
inconsistency rather than an unrecognised risk — which also makes it cheap to fix.

**Fix:** the assignment form, which this repo already uses elsewhere —
`ERRORS=$(( ERRORS + 1 ))`, as in `scripts/defaults.sh` (`failed=$(( failed + 1 ))`).
`(( x++ )) || true` also works but reads as though the increment might fail.

## P-2 — Two destructive cache scripts omit `set -euo pipefail` (LOW)

`bin/clear-app-caches`, `bin/clear-derived-data` (also `bin/clean-ds`, `bin/decloud`).

`bin/nuke-mrk` and `scripts/uninstall` both open with `set -euo pipefail`. These do not.
`bin/clear-app-caches` then runs 20+ unconditional deletions of the form:

```bash
rm -rf "$HOME/Library/Application Support/net.imput.helium/Default/Cache"
```

With `set -u`, an unset `HOME` aborts the script. Without it, `$HOME` expands to empty and
every one of those becomes an absolute path — `rm -rf "/Library/Application Support/…"`.

Likelihood is low: `HOME` is set for interactive shells and by `launchd`. This is recorded
because it is the one place where the repo's own convention is absent and the consequence
of its absence is worst, not because a trigger is known. Module 13's P-10 covered these
scripts for *unattended guards*; the missing `set -` line is a separate gap.

## P-3 — A failed firewall read is recorded as "was off" (LOW)

`scripts/hardening.sh:149-151`.

```bash
prev="off"
fw_state=$(/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate 2>/dev/null || true)
if grep -qi "enabled" <<< "$fw_state"; then prev="on"; fi
```

`|| true` converts a failed read into an empty string, and the initialiser leaves `prev` at
`"off"`. The rollback line written at `scripts/hardening.sh:167` is then
`--setglobalstate off`. If the firewall was actually **on** and the read merely failed,
running `~/.mrk/hardening-rollback.sh` would disable it.

The initialiser is what keeps the rollback line well-formed — without it an empty `prev`
would emit `--setglobalstate` with no argument — so this is a trade, not an oversight. But
it is the same class as the analytics-read bug fixed earlier (a failed read taken as a
known state), at a site that never received the same treatment. The three-way read used for
analytics is the pattern to copy: distinguish *read succeeded and says off* from *read
failed*, and skip writing a rollback line in the second case.

## P-4 — `mrk-status` reports every Brewfile package missing when `brew list` fails (MEDIUM)

`tools/mrk-status/main.go:339-368`.

```go
instF, instC := map[string]bool{}, map[string]bool{}
if out, err := exec.Command("brew", "list", "--formula").Output(); err == nil {
    for _, p := range strings.Fields(string(out)) { instF[p] = true }
}
```

On failure the `if` body is skipped and `instF` stays an **empty map**. The loop below then
tests `if instF[pkg]` for every Brewfile entry, every lookup returns false, and all **127**
packages render as `sevErr` — `pkg (missing)`. The dashboard shows 127 fabricated failures
and gives no indication that the check itself did not run.

The absent-brew case *is* handled: `tools/mrk-status/main.go:332` uses `exec.LookPath` and
reports `brew unavailable — skipping checks`. So the author considered brew missing but not
brew *present and failing* — a broken prefix, a partial upgrade, a permissions problem.

This is the recurring class this repo already names. `scripts/sync:190-194` carries the
guard for the identical call, with the reasoning in-line:

```bash
# Capture with an exit-code check (like brew leaves above): a failed list must
# not silently yield an empty set, which --prune would read as "every tracked
# entry is stale" and offer to delete the whole Brewfile.
if ! _formulae_out=$($HOMEBREW list --formula 2>/dev/null); then
  err "brew list --formula failed — cannot determine installed formulae"
  exit 1
fi
```

`sync` is destructive and so the consequence there was data loss; `mrk-status` is read-only
and the consequence is a false alarm. That difference is why the fix reached one and not the
other. **Fix:** treat the error as a check failure — return a `sevWarn` group saying the
package check could not run, rather than folding it into per-package results.

## Verified clean

These were examined and found correct. Recorded so the next cycle does not re-derive them.

**V-1 — Rollback fidelity holds, in both rollback scripts.** `scripts/defaults.sh`
`write_default` records `defaults write <domain> <key> -<original-type> <original-value>`
when the key exists, and `defaults delete … >/dev/null 2>&1 || true` when it does not — the
absent case correctly rolls back to *absent*, not to an assumed default. The original value
is captured *before* the idempotency check, so re-running `make defaults` preserves the
first run's originals rather than recording the already-applied value. Values are escaped
with `printf %q`. `scripts/hardening.sh` pairs absent→delete with present→write at all
three of its `defaults` sites (`:128/130`, `:136/138`, `:226/230`) and restores
`/etc/pam.d/sudo` from a backup file at `:80`.

**V-2 — No config change was found written outside the tracked mechanism.** Every
`defaults write` in `defaults.sh` routes through `write_default`; every one in
`hardening.sh` is paired with a `rollback` line.

**V-3 — PR #3's ignore list is complete and correctly scoped.** `scripts/sync-login-items:210-233`.
The ignore list drops **add** candidates only; the stale set is deliberately untouched, so
an already-tracked item stays tracked until explicitly deleted. The contradictory case — a
name both tracked and ignored — is surfaced as its own `conflict_items_arr` rather than
being misreported as stale. The comments state the reasoning. Nothing half-finished.

**V-4 — Destructive-on-empty is explicitly handled for the AppleScript read.**
`scripts/sync-login-items:164-183` aborts on a non-zero `osascript` exit **and** on an
empty-but-successful read, with the reasoning in-line: *"'You have zero login items' and
'the read failed' are indistinguishable here, so this aborts rather than offering to delete
every tracked item."* This is PR #1's fix; PR #3 built on it without weakening it.

**V-5 — The STE `DEFAULT_DESCRIPTIONS` split is complete.** PR #4, merged 2026-08-07.
`scripts/defaults.sh` contains 143 `write_default` call sites; the extraction regex in
`scripts/check-defaults-desc` matches **143 of 143**, with zero unmatched. The gate cannot
currently be fooled by a call site it fails to see, and its own report (`143 keys,
descriptions in sync`) agrees with the count.

**V-6 — Eight of the eleven `((x++))` sites are safe, by call context.**
`scripts/post-install:97` is inside `open_extension_urls`, called as
`open_extension_urls … || failed=$(( failed + 1 ))` (`:182`, `:198`, `:214`) — the `||`
suppresses `set -e` for the whole function. `scripts/setup:185/190/195` are inside
`validate_setup`, called as `if ! validate_setup` (`:644`). `scripts/brew:434/566/598/620`
are inside `install_brewfile`, called as `if ! install_brewfile` (`:655`). Reported here
because they will match any future grep for this pattern and should not be re-flagged.

**V-7 — `set -e` arithmetic elsewhere uses the safe form.** `scripts/defaults.sh` counts
failures with `failed=$(( failed + 1 ))` at every one of its 143 call sites.

**V-8 — The Go concurrency dimension is empty by construction.** No `go func`, no channel,
and no `sync` import exists in any of the four modules — every binary is single-threaded
over bubbletea's own loop. `go vet` is clean in all four; `go test -race` passes for the two
with suites (picker, mrk-menu). All four `go.mod` files pin `go 1.22`, so there is no
version divergence between binaries.

**V-9 — The secret scanner already covers the binary-plist blind spot.** `scan_for_secrets`
in `scripts/lib.sh` detects the `bplist00` magic, converts a copy with
`plutil -convert xml1`, scans that, and warns and falls back to raw bytes if conversion
fails; the stored file is untouched. Its case-sensitive / case-insensitive pattern split is
documented against a real past false positive (`AIza…` folded case-insensitively matched a
`<data>` blob in a BetterSnapTool plist). The repo most likely to carry credentials is gated
too: `scripts/snapshot-prefs` scans per file at capture (`:93`, `:194`, `:252`) and runs
`require_clean_secrets` over the whole changed set before committing (`:435`).

**V-10 — Repeated `make` runs do not compound.** No rc-file appends exist in `setup` or
`post-install`, so there is nothing to duplicate. `BACKUP_DIR` is timestamped
(`scripts/setup:100`), so a second run cannot overwrite the first run's backup with an
already-linked state — the most dangerous idempotency failure, and it is closed by
construction. Dotfile linking moves an existing real file into the backup directory and
*verifies the move landed* before symlinking (`scripts/setup:493-500`), aborting if it did
not; links use `ln -sfn`, which is idempotent.

**V-11 — `Makefile` and shell startup.** Every `Makefile` target is either declared
`.PHONY` or has no same-named file to collide with. `dotfiles/.zshrc` guards its one
subprocess-on-startup behind `command -v pyenv` (`:35`).

## What the tooling missed, and why

`make check` is green at `c460f02`: `check-picker-desc` (127 packages), `check-defaults-desc`
(143 keys), `shellcheck`, and `go test` in all four modules.

Nothing here is reachable by that tooling. `shellcheck` does not model `set -e` propagation
through function call context — it cannot know that `((ERRORS++))` is fatal in `run_phase`
and harmless in `install_brewfile`, because the difference is at the *call site*, in a
different function, sometimes hundreds of lines away. P-2 is a missing line, which no linter
flags. P-3 requires knowing what `socketfilterfw` returns on failure and what the rollback
would then do — semantics no static tool has.

The generalisable lesson is V-6's: **for this bug class, the grep result is the beginning
of the analysis, not the end.** Any future sweep for `set -e` hazards must resolve the call
context of the enclosing function before reporting, or it will be wrong most of the time.
