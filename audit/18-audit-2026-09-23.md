# Module 18 — Apple silicon and macOS 26 fitness (2026-09-23)

**Date:** 2026-09-23
**Scope:** the question the owner asked: is mrk optimized for the M5 Pro on macOS 26 it has run
on since the 2026-09-15 migration? That meant checking the parts of mrk that depend on the
architecture or the OS release:
- every Brewfile package, against Homebrew's own definitions
- the Go tools as built for darwin/arm64
- the LaunchAgents
- the CI runner
- the paths that assume a Homebrew prefix
- shell startup

Module 15 covered the macOS 26 behaviour of defaults, harden and trim-services on the Mac itself,
and this module did not repeat it.

**Method:** a cloud container, not the Mac. Homebrew's definitions came from shallow clones of
Homebrew/homebrew-cask (`79315b5`) and Homebrew/homebrew-core (`98cbed4`), both taken on
2026-09-23. `formulae.brew.sh` is outside the container's network policy. The Go tools were
cross-compiled for darwin/arm64 with Go 1.24.7 and 1.23.12, and their load commands were read
with `debug/macho`. Nothing touched the Mac, so nothing was uninstalled.

`check-picker-desc` cannot run on Linux. Its `grep -E '^\t"'` depends on BSD grep reading `\t` as
a tab, and GNU grep reads it as `t`, so it calls every package missing, at `HEAD` too. The same
comparison was run with `grep -P`. On macOS, where CI runs it, the check works.

**Headline: little of mrk depends on the architecture. Five Brewfile apps did, and four
settings needed fixing.**
- Five Brewfile apps needed something the M5 does not have by default:
  - two need Rosetta
  - three install kernel extensions, and a third-party kext on Apple silicon loads only after
    Startup Security is lowered in recoveryOS
- Two settings were right only by accident of the environment:
  - topgrade found npm only through an inherited PATH
  - the Go tools had `LC_UUID` only because the installed Go is new enough
- The LaunchAgents ran at launchd's default priority
- CI ran on macOS 26 only because that is `macos-latest` today, and it will move first

## M-1 — topgrade's npm steps loaded nvm from where mrk never installs it (LOW, FIXED)

Both npm steps in `assets/topgrade.toml` ran
`[ -s /opt/homebrew/opt/nvm/nvm.sh ] && . /opt/homebrew/opt/nvm/nvm.sh`. nvm is not a Homebrew
formula here: post-install clones it into `~/.nvm`, and the Brewfile says so. On a Mac set up by
mrk the test was false every time, and nvm was never loaded.

The steps worked anyway when topgrade inherited a PATH from a zsh that had loaded nvm, which is
the usual case with `update-full` in a terminal. From any other parent, `npm update -g` failed
with "command not found" and `npm cache verify` did nothing, because its `command -v npm` guard
swallowed the miss.

**Fix.** Both steps source `$NVM_DIR/nvm.sh`, the `~/.nvm` they already exported.

**Test.** `tests/topgrade-npm.sh` takes each step's command from the TOML as written and runs it
the way topgrade runs a custom command, through `sh -c`. The environment is cleared, `PATH` is
`/usr/bin:/bin`, and `HOME` is a scratch directory holding a stub `~/.nvm/nvm.sh`, whose `npm`
records its arguments. A real npm elsewhere on the system cannot pass the test, because it
records nothing.

## M-2 — The Go floor allowed a toolchain whose binaries macOS 26.7 refuses (LOW, FIXED)

`assets/CLAUDE.md` records that dyld on macOS 26.7 refuses an executable with no `LC_UUID`. Go's
own linker has written one only since Go 1.24. All four modules under `tools/` declared `go 1.22`.

`mrk-status`, built for darwin/arm64:

| Toolchain | `LC_UUID` |
|---|---|
| Go 1.23.12 | absent |
| Go 1.24.7 | present |

Homebrew's go and CI's `stable` are both newer, so no binary on this Mac lacks it today. Nothing
in mrk required that, though.

**Fix.** `go 1.24` in all four `go.mod` files. `go mod tidy` changes nothing else, and
`go vet` and `go test` pass in each module. With the default `GOTOOLCHAIN=auto`, an older Go now
fetches 1.24 or later itself. With `GOTOOLCHAIN=local` it stops, with
`go.mod requires go >= 1.24 (running go 1.23.12; …)`, rather than building a binary that will
not load.

## M-3 — The LaunchAgents ran at default priority (LOW, FIXED)

Neither plist in `assets/launchagents/` set `ProcessType`, so launchd applied its default, light
limits. `com.user.clear_app_caches` also has `RunAtLoad`: at every login it deletes the browser
caches (2.3 GB in Chrome alone, measured on 2026-09-10) while the login items start.

**Fix.** `ProcessType` `Background` in both. launchd then throttles the job's CPU and disk I/O,
and on Apple silicon keeps it on the efficiency cores. Both plists parse. `install_launch_agent`
in post-install already copies and reloads a plist whose content changed, so this Mac picks it up
on its next `make post-install`.

**Not tested.** No test reads the plists, and none was added. Losing the key costs some
efficiency and breaks nothing.

## M-4 — CI tracked Apple's newest macOS, not this Mac's (LOW, FIXED)

`runs-on: macos-latest`. On 2026-09-23 actions/runner-images maps it to macOS 26 on arm64, which
matches this Mac. The label moves to macOS 27 when GitHub promotes it, while `macos-updates`
keeps this Mac on 26 until its owner upgrades by hand. Module 16 met the same mismatch in pyenv:
an SDK newer than the OS. The workflow now names `macos-26`, with a comment to bump it in the
same change as the Mac's own upgrade.

## M-5 — Five Brewfile apps needed Rosetta or a kernel extension (owner's decisions, DONE)

| Cask | Homebrew says | Why it matters on the M5 |
|---|---|---|
| kobo | `requires_rosetta` | Intel only. Apple has said Rosetta stays fully available only through macOS 27 |
| minecraft | `requires_rosetta` | Intel only, the launcher |
| macfuse | caveat `kext` | Loads only after Startup Security is set to Reduced Security in recoveryOS |
| veracrypt | `depends_on cask: "macfuse"` | The only package in the Brewfile that needs macFUSE |
| samsung-magician | caveats `kext` and `reboot`, `installer manual:` | Two Portable SSD kexts, and an installer brew opens for you to click through, halfway through Phase 2 |

Homebrew offers `veracrypt-fuse-t`, the same VeraCrypt build against FUSE-T. FUSE-T needs no
kernel extension, and its installer includes an FSKit component. That was offered.

**Owner's decision (2026-09-23): remove all five.** kobo and minecraft were removed at the
owner's request. VeraCrypt and Samsung Magician were removed when asked, and macFUSE went with
VeraCrypt, since nothing else in the Brewfile uses it.

The Brewfile and the picker descriptions now agree at 116 packages, down from 121. No other file
named any of the five, except trim-services. Its two Samsung Magician agents stay listed: they
are reported "not loaded" when absent, and still apply wherever Magician is installed.

**Still to do, on the Mac.** `sync` offers any installed leaf again, so these five must be
uninstalled there too.

**Done by 2026-09-28.** Read-only that day: `brew list --cask` holds none of the five, their apps
are gone from `/Applications`, and no macFUSE or Samsung kernel extension is loaded.

## Left open

- **Intel-only apps that Homebrew does not mark.** Homebrew marks a cask only when a maintainer
  knows it needs Rosetta. The App Store apps and casks that ship a single build are unchecked.
  Spotlight indexing is off on this Mac, so `mdfind` cannot find them. `lipo -archs` on each
  app's executable can. → To close: run that over `/Applications` and decide per app. A check in
  `mrk-status` could keep it true.

  **Surveyed 2026-09-28, read-only.** Each bundle's main executable was read with `plutil` for its
  name and `lipo -archs` for its architectures. Spotlight indexing is on here now (audit 16,
  U-6), but the survey did not need it. Rosetta is installed and runs.
  - **Apps:** 98 bundles in `/Applications` and `~/Applications`. 68 are universal and 26 are
    arm64 only.
    - Google Docs, Sheets and Slides are shell-script shortcuts from Google Drive for desktop, so
      they need no Rosetta.
    - The only Intel-only bundle is `Waves AU Reg Utility 12.app` (12.8.0), in
      `/Applications/Waves/WaveShells V12`. Waves Central installs it with the V12 shells.
    - Of audit 16's four (U-10), Kobo and Minecraft were uninstalled (above) and Adapter is
      gone. Kindle Previewer is version 4 now, which is universal.
  - **Audio plug-ins, beyond this item's scope:** 74 bundles in `/Library/Audio/Plug-Ins` and
    `~/Library/Audio/Plug-Ins`. Nine are Intel-only:
    - the Waves V12 shells: `WaveShell1-AU 12.8.component`, `WaveShell1-VST 12.8.vst` and
      `WaveShell1-VST3 12.8.vst3`;
    - five Waves VST2 shells: `WaveShell1-VST` 13.0, 14.12, 14.19 and 14.25, and
      `WaveShell3-VST 13.0`;
    - iZotope's `iZRX12SpectralEditorAUHook.component` (12.0.0).

    The V13 and V14 AU and VST3 shells are native. `WaveShell1-VST 12..vst`, from the
    2026-09-15 install, is a bundle with no executable.

  **Left for the owner:** whether each of these is still wanted. Only Waves Central and iZotope's
  installer can remove or replace their components, and mrk manages none of them. Logic Pro loads
  only AU, so of the nine only the V12 AU shell and the RX hook matter to it. The VST2 and VST3
  shells matter only to a host that loads them. No `mrk-status` check was added.
- **Browser GPU caches.** `clear-app-caches` deletes Helium's `GPUCache`, `DawnGraphiteCache` and
  `DawnWebGPUCache` daily and at login, which it has done since 2026-09-10. On Apple silicon these hold compiled Metal
  pipelines, so the browser recompiles them on its next launch. The cost is small and the space
  saved is small too. → Owner's call: keep them, or clear only the HTTP and code caches.

  **Decided 2026-09-28: clear only the HTTP and code caches.** Measured read-only that day:
  - **They come straight back.** Within an hour of the clear at login, each of Helium's three
    per-profile GPU caches was back to 548 KB.
  - **Chromium keeps them small.** The browser-level `GraphiteDawnCache`, which mrk never
    cleared, was 13 MB.
  - **Chrome's were never cleared.** The script already left Chrome's GPU caches alone.

  `clear-app-caches` no longer deletes them, and its comment says why. `tests/clear-app-caches.sh`
  is new, and ci-check runs it. It checks that every HTTP, code and Slack cache is cleared, and
  that the GPU caches and profile data stay. The old script fails it, and three more mutations
  are each caught. Branch `claude/helium-keep-gpu-cache`.
- **nvm in every interactive shell.** `.zshrc` sources `nvm.sh` eagerly, and nvm is usually the
  slowest thing in a shell's startup. It was not measured here. → To close: `time zsh -i -c exit`
  on the Mac. If nvm dominates, lazy-loading it is a trade: `node` would not be on the PATH until
  first used.

  **Decided 2026-09-28: `--no-use`, not lazy-loading.** Timed in a bare zsh, not a full
  `zsh -i`: oh-my-zsh auto-updates and `check-updates` runs in one, so timing it would have
  changed the Mac.
  - **The cost.** Sourcing `nvm.sh` took about 250 ms, and its closing `nvm use default` was
    about 220 of that.
  - **The fix.** `.zshrc` now sources it with `--no-use` (29 ms) and puts the newest installed
    Node matching the default alias on the PATH itself. It falls back to `nvm use` when no
    installed version matches the alias.
  - **The result.** The whole block, nvm's completion included, against the real `~/.nvm`: about
    330 ms before and 44 ms after, once warm. The same Node, v24.21.0.
  - **The test.** `tests/zshrc-nvm.sh`. Branch `claude/zshrc-nvm-no-use`.
- **Startup Security.** If macFUSE's or Magician's kext was ever approved on this Mac, its Startup
  Security is still Reduced. → To close: once both are uninstalled, check it in recoveryOS
  (Startup Security Utility) and set it back to Full Security if nothing else needs it.
